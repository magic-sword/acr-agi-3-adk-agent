# 物体認識から行動計画への引継ぎ

更新：2026-09-29。認識は[認識の統合資料](visual-recognition-adopted-ja.md)、行動計画は[計画の統合資料](planning-adopted-ja.md)を正本とする。このページは現在の引継ぎ事項だけを残す。

## 実装済み

既定は**初回SAM＋通常の画素更新**（`COGNITION_PROPOSALS=sam_initial`）。初回・RESET・レベル切替でSAMを使い、通常は一意の画素対応を追跡する。無変化なら抽出も再利用。全候補索引、観測内IDと追跡ID、受理した対象参照の継続／欠落を既存の意味質問へ接続済み。

89フレームの統合検証で候補回収は合成242/264・実ログ133/133、移動は104/127・6/6。実ログの初回後の観測処理は平均6.70ms（Qwenを除く）。全206テスト、実Qwenの1トークン接続3問、実SDKの2操作を確認した。数値の条件・限界は[統合資料](visual-recognition-adopted-ja.md)、実行設定は[ランタイム仕様](hybrid-perception-runtime-20260928-ja.md)を参照。

## 現在の判断

**前処理の精度だけで方式を決めず、後段の計画・因果推論に必要な情報から逆算する。** 物体の厳密な分割・全クラスの確定を必須にせず、曖昧な候補や対応仮説を許容する。動かない「青い四角」も後で役割を検討できるよう残す。

全候補・連動関係を保持することと、モデルへ一度にすべて提示することは別。大量の連動情報がノイズになる可能性があるため、どの情報を集計・要約・提示するかは未確定。連動グループを同一物体や因果関係と断定しない。

[直近の検証と判断](visual-recognition-adopted-ja.md#現時点の判断と直近の検証)に結果を集約した。差分を渡したモデルの39/51と、プログラムによる連動集計の8/8は別の評価範囲で、優劣は未確認。連動集計の本番統合、追跡器の削除、画像の一律省略、全連動の常時提示は採用していない。

## 行動計画の引継ぎ

**長い逆算計画の最適化は一区切りとし、現在は候補生成・履歴形式・対応付けの設計を引き継ぐ。** 採用方針と根拠、不採用案の短いまとめは[行動計画の統合資料](planning-adopted-ja.md)に集約した。

- 行動計画の必須入力は、目的、少数の対象と抽象操作候補、判断に必要な現在状態・試行結果の3要素。
- コンパクトな逆算計画で、最終ゴールに向けて達成・検証する小目標を生成する。
- 行動計画は動詞と対象を組み合わせ、高速モードが連続操作・位置合わせ・終了確認を担う。
- 現在値の併記や長い計画の最適化は採用・追加追求しない。以前の資料にある「次の検証」を自動的に再開しない。

通常経路は `FocusedRuntime` へ変更済み。交換可能な暫定候補生成、コンパクトな小目標生成、入力3要素、既存の高速実行・結果照合を接続した。汎用ノート巡回と重複するスキル選択は通常経路から除外した。実装・限界は[計画の統合資料 §6](planning-adopted-ja.md#6-通常ワークフローへの実装)を参照。**以下の候補ごとの履歴対応付けは未実装**であり、直近の比較・XAIは通常経路を変更しない入力実験である。

## 次のセッションへ：候補生成と履歴形式を設計する際の前提

ユーザーは、候補生成システムと履歴の書き方を今後検討する際に、今回の情報を考慮する方針。今回の依頼は引継ぎ資料への明記であり、新たな実装・実験の開始指示ではない。以下を実装済み・一般化済みの結論として扱わない。

### 根拠になった検証

- 候補・履歴・小目標の切り分け56要求：別対象の候補を与えれば履歴を残しても選択は変わるが、多様な候補の32要求中30件で先頭を選択。候補の強化だけで十分とは確認できなかった（計画資料 §7）。
- 候補数46要求：2候補でも正解を後ろに置くと誤り、46要求中44件で先頭を選択。件数を減らすだけでは改善せず、許容上限は未確定。通常の上限3件は暫定のまま（§8）。
- XAI 24要求＋再現確認4要求：2・3候補の合成課題で、**同じ試行事実を対応する候補へ移すと、両例で末尾の正解を選択**。履歴の削除では先頭への選好が強まった。候補と結果の対応付けが有力な問題箇所だが、実画像上の対象対応を自動で解けたわけではない（§9）。
- XAIは入力介入と出力トークン確率の解析。注意重みの直接測定でも、ゲーム成功率の実証でもない。理由文と選択ID・実行対象が矛盾する例もあり、理由文を内部思考の証拠としない。

### 検討の出発点とする設計方針

**候補と履歴は別々に保存し、プログラムが根拠のある対応付けを行い、行動計画には候補と関連する事実を一体化して渡す。** 候補生成モデルだけに履歴の対応付けを任せない。

```text
小目標生成 → 候補生成 → プログラムによる履歴照合 → 行動計画
                                                   ↓
履歴へ保存 ← 結果照合 ← 高速実行・受付・次の観測
```

履歴照合を新しいLLMステートにする必要はなく、候補生成と行動計画の間のプログラム処理として検討する。

| 担当 | 責務 |
|---|---|
| 候補生成モデル | 現在の対象参照、抽象動詞、期待効果・今回確かめたいことを提案する |
| プログラム | 観測内ID・追跡対応・実行起動ID・受付記録などを検証し、関連する過去試行を取得する。対応の根拠と不確かさを保持する |
| 行動計画モデル | 対応付きの結果と今回の条件差を踏まえ、再試行・別対象・別手段を選ぶ |
| 結果照合 | 実際の操作と観測を保存し、因果解釈・仮説は事実と区別して記録する |

結び付ける中心は**過去の思考文ではなく、実際に何を操作して何が観測されたか**。過去の理由文や仮説を毎回再掲して対象への誘導を強めない。長期の条件付き知識・スキルと、頻繁に変わる現在状態・短期試行は別に扱う。

対象名や外見が同じというだけで結び付けない。同じ白い四角が複数ある場合、追跡切れ、再出現、RESET・レベル境界、状態・操作条件の変化を考慮する。観測内IDは別観測へ持ち越さず、追跡対応も物理的同一性の証明とはみなさない。

- 同じ対象への試行と確認できる：条件・根拠・出典を付けて提示する。
- 同じ対象の可能性はあるが曖昧：確定結果に混ぜず、不確かな関連として提示する。
- 対応不明／検索できない：**「未試行」と断定せず「履歴との対応不明」**とする。未試行という主張には履歴の網羅範囲も必要。

記録形式は未確定だが、設計時は対象参照とその観測、抽象操作・実際の操作、起動ID、受付、前後観測、実測結果、当時の条件、モデル解釈を区別できるようにする。計画に渡す候補カードは「対象・動詞／今回確かめたいこと／対応する試行と実測結果／今回との条件差／対応の確実性」程度に絞る。これらは設計項目であり、保存スキーマを確定したものではない。

「クリック受付済み・画素変化なし」を「対象は作動しない」と一般化しない。正確な座標と照準確認は実行側に保持し、行動計画には原則として意味的な対象と結果を渡す。候補生成・履歴照合が、未確認の因果関係や対象同一性を補ってしまわないようにする。

### 再開時の検証観点

まず対応が確実な場合、曖昧な場合、同形の別対象、追跡切れ、状態変更、境界越え、実行未受付を扱い、誤った履歴が混入しないことを確認する。その上で、候補順・番号・履歴順・対象名を変えても目的に合う選択が保たれるか、選択ID・理由・実行対象が一致するかを確認する。少数候補で成立してから件数上限を再評価する。

未試行候補を先頭へ置くだけ、同じ操作を一律禁止するだけでは改善と判定しない。以前不採用とした長い逆算計画への現在値併記と、今回の単段選択への対応付き試行事実の提示は別の検証として扱う。今後の比較では合成課題の効果が実盤面でも保たれるかを確認する。

## 認識側に残る留意点

対応保留による再確認の過剰発火、色変化・同形物体での対応切れ、測定と自由文の説明の矛盾は、認識だけの正答率で解消済みとしない。以前のls20ログでは、黄色いバー端の変化を後続照合がプレイヤー移動と説明した。[比較HTML](../outputs/measured-runtime-20260928/gallery.html)・[原因分析](history/visual-recognition/cognition-handoff-analysis-20260928-ja.md)。これらは既知の未解決例であり、今回の資料整理による新しい作業指示ではない。
