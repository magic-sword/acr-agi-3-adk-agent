# 認識・計画・高速実行の引き継ぎ

更新：2026-09-29。対象認識、目標を分解する計画、抽象操作を具体的な1アクションへ変換する高速実行について、実装内容と検証結果をまとめる。

## 現行構成

```text
SAM／画素追跡／対象ID・全体と部品の仮説
  → 状況理解と最終目標 → 小目標生成 → 動詞＋対象の候補 → 実行手順
  → 高速実行：現在の手順と画面から具体的な1アクションを選択
  → 操作送信・受付・観測 → 同じ手順を継続／節目で結果照合・計画更新
```

通常ランタイムは `FocusedRuntime`、メモリschema 16。`create_runtime` から候補生成器を差し替えられる。計画手順は複数ステップを保持できる。高速実行は1トークンで具体操作またはステップ完了・再検討を選ぶ。毎操作のたびに全計画を作り直すわけではない。

クリック座標は現在の対象マスク内からホストが選ぶ。カーソル位置合わせのモデルループは使わない。汎用ノート巡回、別途のスキル選択ステージ、旧比較ランタイムも使わない。現在の状態遷移図は計画5工程と高速実行を表示する。

## 実装済みの内容

1. **対象認識**：SAMマスク・元の画素断片から対象仮説を生成。対象IDと対応の不確かさ、全体／部品・接触・共通運動を保持する。[対象認識](object-hypotheses-runtime-ja.md)。
2. **計画**：状況と最終目標を理解し、小目標へ分解する。動詞＋対象の候補から操作を選び、複数ステップの実行手順を保持する。候補生成器は差し替え可能。
3. **高速実行**：現在の抽象操作・手順・画面から、具体的な1アクションを1トークンで選ぶ。同じ手順の実行中は計画を保持し、必要な節目で結果照合する。クリック位置は現在の対象マスクからプログラムで決定する。
4. **検証完了の条件**：検証目的の操作では、操作受付とその後の観測が得られるまで完了を選べない。効果が不明な状態と、対象や操作が利用できない状態を区別する。
5. **履歴の軽量化**：計画対象の変化・無変化・不明と、別対象に実測された変化だけを記録・提示する。候補に対応する履歴はプログラムで取得する。[履歴の検証](compact-history-validation-ja.md)。

単一操作版 `SimpleRuntime` は比較・回帰確認用。通常経路では、計画と高速実行を分担する `FocusedRuntime` を使う。

## 履歴・認識の留意点

- 無変化は0、測定不能は `unmeasured`／`null`。無関係な対象の無変化を大量に渡さない。
- 操作受付、対象マスクへの命中、画素変化、モデルの因果解釈は別物。画面の隅の変化を操作対象への効果と断定しない。
- 対象IDや共通運動は物理的同一性の証明ではない。同一性区間・分裂／合体・境界を考慮する。
- 候補に対応する短い履歴はプログラムで取得し、汎用的な記憶巡回LLMを挟まない。
- 一度の成功や無変化を普遍的な法則・スキルとして扱わない。

## 計測済みの値と限界

以下は**単一操作版の比較実験**であり、現行の計画版の速度ではない。

| 単一操作版の履歴 | 4手目の入力 | 4回の判断合計 | 初回SAM込み総時間 |
|---|---:|---:|---:|
| 軽量化前 | 12,763トークン | 31.4秒 | 68.9秒 |
| 軽量化後 | 3,311トークン | 17.1秒 | 55.8秒 |

同じ履歴の変換では、4手目の履歴量が25,743文字から3,252文字へ約87%減。CPU SAMは初回約37秒で、毎操作のコストではない。GPUでの比較は未実施。モデルサーバーのGPU設定はあるが、NVMLの実測確認は失敗している。

**全241テストが成功**。抽象操作・小目標・複数ステップ・高速実行に加え、認識・履歴縮約・受付・パッケージを検証した。2段階手順のテストでは、同じ抽象操作を保持したまま高速側が上・下の具体操作を選び、途中に理解・再計画やカーソル呼び出しがないことを確認した。認識再生は89フレームで確認済み。

実モデルの試走では、計画からクリック1回を実行し、観測・結果照合まで進んだケースがある。一方、最新の試走では観察だけで満たせる小目標を生成し、操作せずに完了を選んだ後、再計画中に100秒の判断枠に達した。操作数・到達レベルはともに0。テストの成功は攻略性能や実行速度の保証ではない。

試走ログは `outputs/planning-restored-20260929/` に保存。`verified/` が1操作を実行した試走、`release/` が最新コードの試走、`tests.log` が全テストの記録。最新試走の停止理由は `candidate_provider_invalid` だが、候補生成の例外処理はタイムアウトも同じ理由にまとめるため、候補内容の不正だけが原因とは断定できない。

## 残る課題と進め方

- 観察だけで完了する小目標を避け、目標達成や仮説検証に必要な操作へつながる計画の品質を評価する。
- 再確認ループ、SAM初期化、入力の膨張、出力生成の時間を別々に測り、改善を一つずつ検証する。
- 候補生成のタイムアウトと出力不正を、停止理由で区別できるようにする。
- 繰り返し操作の有効性と、無変化からの過剰な因果解釈を評価する。一度の成功を一般的な法則としない。
- 高速化でも、目標を分解して計画を保持する役割と、抽象操作を具体操作へ変換する役割を維持する。
