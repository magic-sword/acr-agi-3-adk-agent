# 領域から対象仮説への統合と対象別の試行履歴

実装日：2026-09-29。通常の `FocusedRuntime` に、領域候補より上の対象仮説と履歴対応を追加した。**元の候補を保持し、部品・全体・連動する集合を併存させる。対象の同一性が曖昧なら、過去結果の対応も曖昧なものとして提示する。**

これは認識・記憶の実装方針であり、未知ゲームの攻略性能や物理的な物体認識の正しさを保証するものではない。行動計画の3要素と交換可能な `CandidateGenerator` は維持する。

## 1. データの流れ

```text
SAMマスク・プログラム領域・元の連結成分
  → 観測内の領域ID／領域の追跡ID
  → 対象ID・部品構成・統合仮説・対応の不確かさ
  → 現在対象の選択
  → 対象ID付きの動詞＋対象候補、対象に関連する試行履歴
  → 実行、対象自身と別対象の変化を分けた結果照合
```

主な実装は [object_memory.py](../agent/cognition/object_memory.py)、マスク形式は [region_masks.py](../agent/cognition/region_masks.py)、通常経路との接続は [focused_workflow.py](../agent/cognition/focused_workflow.py)。メモリschemaは14。

## 2. マスクと部品を残す

- SAMの外接矩形に加え、元の盤面座標のマスクを `[y, x_start, x_end_exclusive]` の行ランで保存する。
- SAM入力は盤面の6倍拡大なので、各6×6ブロックの半数以上がマスク内なら元の1画素を含める。この縮約も推定であり、境界の正解を保証しない。矩形は従来と同じ外向き丸めを使う。
- 同じ矩形でもマスクが違えば別候補として保持する。矩形だけの既存プロバイダーも受理するが、矩形を前景マスクと見なさない。
- プログラムが多色矩形や盤面をまとめても、元の同色連結成分を追加候補として残す。元成分は最大256件で、超過を `extraction_limited` に記録する。
- 領域の追跡は従来の枠内画素の一意な完全一致を利用し、マスクも同じ変位で移す。色変化などを測定上の完全一致に昇格させない。
- マスクは測定・監査・命中確認に保存する。通常のモデル入力と短い意味質問からは除き、索引と要約を渡す。

## 3. 統合は仮説として追加する

| 種類 | 作り方・意味 |
|---|---|
| `region` | 一つの測定候補。物体全体とは限らない |
| `spatial_group` | 接する元成分をまとめた候補。接触した別物体の可能性も残す |
| `co_motion_group` | 近接する元成分が2回以上、同じ非ゼロ変位で移動した集合。同期した別物体かもしれない |
| `interpreted_group` | モデルが複数領域を一つの対象として選択した仮説。測定による一体性の確認とは区別する |
| `part_of_hypothesis` | マスクの厳密な包含による直接の親子候補。意味的な部品関係の確定ではない |

接触・共通運動の探索は面積128以下の元成分の先頭128件を対象にする。共通運動ではマンハッタン距離2以内の近接を許し、1画素の隙間を挟む部品も扱う。静止だけでは共通運動の回数を増やさない。変位が異なる場合は共通運動の支持を引き継がない。

自動統合は2〜8成分、外接面積256以下、最大64群という暫定上限を置き、除外数と探索上限を索引に記録する。これは背景判定や物体サイズの普遍的ルールではない。統合対象外でも元の候補は残る。モデル選択で作った群は、構成員が追える限り保持する。

モデルが選んだ群の部品間の相対配置が変わった場合は、対応区間を更新して過去結果を保留付きにする。関節を持つ一物体か、別物体だったかは自動確定しない。

## 4. 同一性と履歴の対応

対象IDは登録時に発行し、名前・位置・色から毎回作り直さない。RESET、レベル境界、観測系列の断絶では区間を分ける。

| 状況 | 扱い |
|---|---|
| 領域の追跡IDが継続 | 対象IDと対応区間を継続。物理的同一性の証明ではない |
| 追跡は切れたが、同じ位置・同じマスクへの対応が双方で一意 | `appearance_hypothesis` としてIDを継続し、`identity_segment` を増やす |
| 領域追跡が複数一致・競合 | 同じ位置に候補があっても同一性を強制しない |
| 分割・統合の可能性 | 新しいIDに過去対象の `predecessors` を付け、対応を仮説として残す。履歴本文を複製しない |
| 曖昧な対応の後に追跡が安定 | 直前の追跡は `tracked` でも、曖昧になる前の履歴との対応は保留のまま |

分割・統合の対応候補は、マスクの重なりが小さい側の面積の半分以上というヒューリスティックで最大8件。これは対応を確定する閾値ではない。長い遮蔽後の再同定や完全な多仮説追跡は実装していない。

試行には、起動ID、対象ID、開始時の対象スナップショット、指定した部品、基準状態、操作受付、実測、モデル解釈を保存する。対象解釈が変わっても開始時の記録は書き換えない。

同じ起動を複数回照合しても、履歴検索では最新の照合1件として扱う。未実行・受付不明の計画は操作済みの履歴として検索しない。実操作の詳細が直近8件の窓から落ちた場合は、起動内の省略件数を明示する。

クリック位置は操作前のマスクに対して照合する。結果照合には、**選択対象自身の無変化も含む観測**と、**別対象の観測**を分けて提示する。画面全体の1画素変化を、そのまま選択対象への効果とはしない。領域上の画素変化・命中と因果解釈は別の記録である。

## 5. 行動計画への接続

- `understand` に全対象IDの索引を渡す。現在対象は最大4件で、`object_id` を選択できる。領域参照から一意に対応する場合はホストが補う。
- 候補は `object_refs` で対象を、`candidate_refs` で必要に応じて操作部品を参照する。未知ID・現在対象にないID・選択対象に属さない部品を拒否する。
- 既定モデルには、対象IDが利用可能な場合、`object_refs` を必須にし、選択肢を提示済みIDへ限定する。交換プロバイダーは領域参照だけでも一意なら対応可能だが、対象を参照しない候補は受理しない。
- エピソード内の直近128試行から対象IDと対応区間で検索し、同じ動詞を優先して最大3件を対象／行動候補へ添付する。条件の一致を自動証明する検索ではなく、元の条件・部品・期待効果を併記する。
- 分割・統合の関連履歴は `tentative_identity_or_lineage` と明記する。「検索結果なし」は「未試行の証明」ではない。
- 対象に結び付けて支持した既知スキルは、その対象IDと対応区間が一致する場合だけ再利用候補へ提示する。別対象や曖昧な対応先への転用は新しい試行として提案する。
- 計画の主入力は引き続き `purpose / candidates / evidence`。全マスクや全履歴を計画へ追加しない。
- 索引には位置と色を併記し、対象名には外観を使わせる。高速実行・照準には選択IDに対応する最新の位置・色・領域参照と、欠落した対象IDを渡す。古い位置を現在の事実として再使用しない。

監査ログには `object_hypotheses_updated` と試行時スナップショットを保存する。監視画面には対象索引、対象ID付き候補、試行履歴の要約を追加した。

## 6. 検証方法と範囲

回帰テストは [test_object_memory.py](../tests/test_object_memory.py) と [test_focused_workflow.py](../tests/test_focused_workflow.py) を中心に、マスクの穴、同じ矩形の別マスク、部品保持、色変化、同形コピー、分割・統合、相対配置の変化、境界、別対象への効果、古い履歴検索、出力スキーマ、既知スキルの誤転用を確認する。

保存済みの合成6系列66フレーム・実画面3系列23フレームは [benchmark_object_memory.py](../scripts/benchmark_object_memory.py) で再生する。正解注釈は認識処理の後にだけ使用する。マスクIoU 0.9以上で対象を照合し、対象×フレームの回収、照合対象IDの切替、履歴対応、入力サイズ、処理時間を記録する。

従来の「枠の余裕・対象画素90%・面積倍率」による回収率とは指標が違う。また、実画面は部分注釈なので全体の適合率は測れない。履歴の評価も、正解マスクで対象を選んだ場合の検索検証であり、モデルが正しい対象を選べる成績ではない。

```sh
docker compose exec -T dev python -m unittest discover -s tests -v
docker compose exec -T dev python scripts/benchmark_object_memory.py \
  --sam live --output outputs/object-memory-new/live
```

GPUが使えない検証環境では、`-e COGNITION_SAM_DEVICE=cpu` を指定する。今回の開発コンテナはユーザー名の登録がなく、CPUの初期化に `-e USER=prog -e LOGNAME=prog` も必要だった。既存の描画テストにはDejaVuSansフォントを環境側で補った。

実SAMの初回マスクを保存した後は、`--sam cached --mask-cache <live出力>/frames.jsonl` で同じネイティブマスクを再生できる。SAMが `ready` でないログを成功したマスクキャッシュとして使わない。`--sam recorded` は旧実験の矩形だけを使う比較用であり、SAMマスクの検証には使えない。

### 2026-09-29の検証結果

最終コードの回帰テストは**全286件通過**。同じ起動の重複集計、複数対象の一部だけの曖昧さ、未実行の計画の除外も含む。

実SAMをCPUで初回実行した9系列のマスクを保存し、最終コードへ再生した結果：

| 指標 | 合成6系列 | 実画面3系列・部分注釈 |
|---|---:|---:|
| フレーム数 | 66 | 23 |
| マスクIoU 0.9以上の候補回収 | 262/264 | 130/133 |
| 前後とも回収できた対象の照合ID切替 | 45/235 | 40/113 |
| `tracked` として検索された履歴 | 488 | 151 |
| うち別の注釈対象の履歴だった件数 | 0 | 0 |
| 保留付きの対応として検索された履歴 | 23 | 77 |

履歴の分母は同じ試行を後続観測から検索した延べ件数で、独立した実ゲームの試行数ではない。対象IDの切替は接触・同形コピー・外観変化などで残る。誤帰属0も、正解注釈で選べた対象に対する限定した検索検証であり、曖昧な履歴の対応が正しかったことや実モデルの対象選択の正しさを意味しない。

CPUの実SAM初回処理は約34〜46秒。モデル呼出しを含まない対象更新は、最終再生の `frames.jsonl` で各フレームの時間を記録する。GPUの従来測定とは比較しない。外観付き索引の `understand` テキストコンテキストは今回約21KB以下だったが、画像とツールSchemaは別である。

実Qwen＋実SAMの接続確認では、対象ID付きの状況理解・候補生成・計画まで通った。索引の色・位置を併記すると内部分類名をそのまま対象名にする状態から外観の記述へ変わった。一方、**vc33の最終試走は計画の再確認を繰り返し、100秒の判断枠で操作0・到達レベル0**。対象粒度と履歴接続の実装を、行動更新や攻略の改善が実証されたものとは扱わない。認識の再生検証と、計画の有用性の検証は分ける。

| 保存物 | 内容 |
|---|---|
| `outputs/object-memory-20260929/tests-final.log` | 最終286テスト |
| `outputs/object-memory-20260929/cpu-live-validated/` | 実SAM初回マスク・CPU実行の生ログ |
| `outputs/object-memory-20260929/release-replay/` | 最終ソース・入力ハッシュ、89フレーム、対象・履歴の再生集計 |
| `outputs/object-memory-20260929/runtime-grounded/` | 実モデルの要求・応答、対象ID、再確認ループの記録 |
| [機械可読の検証記録](object-hypotheses-validation-20260929.json) | Git管理する集計・実行条件・限界 |

途中の `live/` はCUDA不在でプログラムへフォールバックし、`cpu-live/` はユーザー名欠落でSAMの初期化に失敗した。これらを実SAMの成功結果に数えない。`runtime-smoke/` はSAM初期化失敗時のフォールバックで2操作、`runtime-sam-smoke/` は対象ID省略による検証エラー、`runtime-final/` は必須ID修正後に再確認ループで停止した経緯を残す。現在の既定モデル用Schemaでは対象IDを必須にした。これ以上の計画プロンプト最適化は今回の対象表現の変更には含めない。

`outputs/` はGit管理外なので、環境移行時は別途保存する。

上記の学習モデルや最適な情報獲得行動の選択器を再実装したものではない。今回の統合ルールと上限は暫定であり、全対象を完全に意味分類する仕組みではない。
