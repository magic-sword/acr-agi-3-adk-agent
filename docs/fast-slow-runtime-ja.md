# 熟考と1トークン実行を分ける認知ループ

2026-09-26。旧attentionポリシー、段階別の物体解釈・実験・スキル昇格の実装は削除した。
本番経路は `CognitiveRuntime` の一つだけで、ADK Workflowが判断と実操作の選択を分ける。

## 熟考で作るもの

`submit_plan` に観測ID、解釈、目標、逆算した計画、因果関係の短いメモ、実行手続きを提出する。
手続きには適用条件、期待する効果、各段階の目的・完了条件・再考条件・操作候補を持たせる。
クリックは元画面の具体的な座標を指定する。未知のルールには一操作の探索手順も作れる。
全物体一覧を作る必要はない。因果メモや手続きはモデルの仮説として保持し、事実と見なさない。

手続きは名前で再利用・置換できる。ゲーム内で最大16件を保存し、熟考入力には直近から
最大4件・合計10000文字以内の手続きを渡す。再利用候補は現在の合法操作と座標で再検証する。
レベル／RESET境界では現在計画と実行段階を解除し、保持した知識を熟考で再解釈する。

## 高速側の仕事

スキル選択は計画の候補から1〜4、または8を返す。実行中は現在の手順を保持し、
操作候補1〜6、7、8から一つ返す。llama.cppへ `max_tokens=1` と単一文字の文法を渡す。
長いJSONや理由文を生成せず、コードがラベルを操作に変換する。

- 操作ラベル：観測に対して合法性を確認して1操作を選ぶ。受付と次の観測を待つ。
- 7：現在の完了条件を満たしたというモデル判断。操作を送らず次の段階へ進む。
  最後の段階なら次の候補スキルを選択し、候補が全て終われば次の目標を熟考する。
  完了した段階・条件・観測IDを直近6件まで保持し、熟考へも渡す。完了判断そのものも
  誤りうるため、熟考では盤面と照合する。判断履歴はリプレイでも確認できる。
- 8：予想外／判断不能／計画が合わない。操作を送らず熟考へ戻る。
  直前の期待効果、実測、現行計画、実行していた段階と復帰履歴を渡して再計画する。

8は画面ハッシュや反復回数による拒否ではない。繰り返しが必要なら同じ操作を継続できる。
7もゲーム勝利を宣言するものではなく、勝利・レベル達成はゲーム側の状態を使う。
高速側の不正応答や、途中で操作・座標が非合法になった場合も熟考で再選択する。

通常の継続は1回の高速呼出し。初回は熟考→スキル選択→操作選択が必要で、段階移行・
復帰には複数回呼び出す。意味の判断を一律の呼出し回数で制限せず、ゲーム全体の期限と
1観測あたりの判断期限 `COGNITION_DECISION_SECONDS`（既定45秒）で制御する。
計画の構文・契約エラーだけは `COGNITION_REPAIR_ATTEMPTS`（0/1）で修正回数を指定する。

## 入力と実行の境界

画像を先に、変化する質問・状態を後に置き、同じ画像で複数の選択を行う場合の
プレフィックスキャッシュを利用する。変化がある場合に直前画像も渡す。熟考では必要に応じて
前回計画時の画像も渡す。高速側には全スキルや長い因果メモを渡さない。

ホストは差分座標と直近8試行を記録する。微小変化をタイマーと分類したり、画面端を
無視したりする自動判定は導入していない。タイムバー誤認が解消する保証はない。
高速側は期待効果と実測を比較できるが、復帰／完了の判断品質は実モデル評価が必要。

同じ観測の再提出には保存済みの同じ決定を返す。操作を再送する意味ではない。
送信→受付→次の観測の順序を保ち、受付不明では停止する。古い観測ID・非合法な操作・
範囲外クリックを拒否する。全推論後に実時間を確認し、期限切れなら操作を選ばない。

## 記録と検証

`model.jsonl` の `work` は `deliberate` / `choose_skill` / `execute_step`。
高速応答の生の確率、キャッシュ・時間・トークン数を記録する。確率は成功率とは見なさない。
`artifacts.jsonl` に `plan_created`, `cognition_updated`, `fast_selected`,
`reconsider_requested`, `skill_started`, `skill_completed`, `action_feedback` を記録する。
リプレイの「計画・スキルを読む」では表示時点の計画・段階・復帰履歴を確認できる。

回帰テストは実ADKディスパッチと模擬HTTPで、計画の再利用、1トークン実行、7での進行、
8での復帰、不正応答の扱い、予算、受付、境界、記録とリプレイの時系列を検証する。
速度の事前調査は[調査資料](fast-slow-runtime-research-ja.md)を参照。

選択肢は方向名と混同しにくい数字を使い、スキル選択には操作ボタン一覧を含めない。
出力を1トークンに制限しても画像認識や選択の正しさは保証されず、Jevの学習済み並列
予測ヘッドを再現する実装でもない。画像入力・プロンプト処理の時間は依然として必要になる。

## 実装後の確認結果

`python -m unittest discover -s tests -v` は56件成功。提出ノートブックを再生成し、
全コードセルの構文と状態図SVGを検証した。実記録3ゲームのリプレイと計画パネルも表示確認した。

実モデル評価は [20260926T133025594495Z](../outputs/evaluations/20260926T133025594495Z/report.md)。
各ゲーム最大6操作・全体90秒・一観測45秒の短い試行で、クリアしたレベルは全て0。

|ゲーム|操作数|熟考の中央値|高速操作選択の中央値|停止理由|
|---|---:|---:|---:|---|
|ls20|2|7.16秒|0.33秒|一観測の判断期限|
|vc33|6|6.29秒|0.22秒|指定した操作上限|
|ft09|1|7.13秒|0.17秒|一観測の判断期限|

高速応答は1トークンになったが、プレイ全体の改善は確認できていない。
今回の実モデルは8を一度も選ばず、7による手順完了と同じ計画の再生成を繰り返した。
特にft09は盤面が変わっていないのに完了と判断している。完了判断を熟考へ渡す経路は
実装したが、それだけでは誤判断・固執は解消しなかった。ls20・ft09の停止は反復操作の
拒否ではなく、再計画の繰り返しによる時間切れである。

したがって、この実装は二段階の実行・復帰・記録を試せる基盤であり、1トークンでの
完了／予想外の識別精度と、熟考で計画を修正する能力は引き続き評価が必要。
模擬応答のテストで確認した8の復帰動作と、実モデルが適切に8を選べることは区別する。
