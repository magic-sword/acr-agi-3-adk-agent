# ゴール仮説とプログラムの逆算による判断ループ（2026-09-30）

[逆算計画の精査](backchain-review-ja.md) の §6.4（V6）の方針を実装し、3つの環境で評価した。旧方式（毎手の understand・backchain・candidates・ground・reconcile）は `COGNITION_PIPELINE=stages` で使える。既定は新方式（`goal`）。

## 1. 仕組み

| 部分 | 担当 | 実装 |
|---|---|---|
| 状態の述語（内側・重なり・同じ列／行・隣接・同じ色・色が〜・同じ形・消えた） | プログラム | [predicates.py](../agent/cognition/predicates.py) |
| 逆算：学んだ規則（移動、クリックで離れた物体が動く、色の変化）を演算子として盤面をシミュレーションし、ゴールの述語を満たす最短の操作列を探す。見つからなければ、効く規則のない条件（足りない因果関係）を返す | プログラム | [goal_planner.py](../agent/cognition/goal_planner.py) |
| ゴールの仮説：物体一覧と画像から、述語で3つ（温度0.7）。面の始めと、仮説がすべて否定・行き詰まりになったときだけ | Qwen | [goal_runtime.py](../agent/cognition/goal_runtime.py) の `hypothesize` |
| 実行：計画の1手目を押し、毎手、実際の盤面から計画し直す（予測の外れは規則が吸収する） | プログラム | 同 `_think` |
| 否定：条件が成立したのに面が終わらない、または30手使っても条件に届かない | プログラム | 同 `_discard` |
| 何を試すか：計画がつながらないとき、未試行の対象（使っていないボタン、クリックしていない物体、訪れていない物体）から選ぶ | Qwen | 同 `probe` |
| 経験の持ち越し：面をクリアした仮説を色で抽象化して、次の面の最初の仮説にする | プログラム | 同 `_reground` |

### 試走で見つかり、直した一般的な欠陥

- 本番の知覚（SAM）では、物体の色が番号で入っていた（テストの知覚では名前）。
- 物体の形が少し変わると ID が変わる。見失った物体は、同じ色で最後の位置に最も近い物体へ付け替える（`_rebind`）。
- 「まだクリックしていない」の判定が、実際にクリックする位置と別の部分を見ていた。
- 毎手変わるカウンターを、試す対象として選び続けていた。
- 仮説の出力が不正なときの遷移が未登録で、2回が途中停止した。すべての工程にこの遷移があるかをテストで確かめるようにした。
- 試しても動かなかった方向キーを、「決まりどおりに動く」と仮定し続けていた。
- 最初から成り立っている仮説を、3つまとめて差し戻していた。個別に取り除くように直した（この修正後の評価は未実施）。

## 3. 次の課題

1. **ゴール仮説の出し方**（最優先）
   - 一般的な知識（コア知識）に基づく手がかりを、プログラムが列挙する。例：枠で囲まれた領域、操作できる物体と同じ見た目の印、そろっていない同色の組。
   - Qwen には、その手がかりを見せたうえで仮説を出させる。V3 で見つかった「一覧の先頭を選びやすい偏り」を避けるため、並びはランダムにする。
   - 手が速くなったので、多くの仮説を実際に試して否定していく戦略も現実的になった。ただし ARC-AGI-3 は手数の効率も評価するので、その兼ね合いを考える。
2. **評価の条件**：手数の上限を増やして（例：150手）、新方式を評価し直す。
3. 最初から成り立っている仮説を個別に取り除く修正の効果を測る。

## 4. 方針の修正と V7：ゴール仮説の出し方（2026-09-30）

ユーザーの指摘により、手数が成績に直結する ARC-AGI-3 では、系統的な探索（状態グラフ）を土台にしないことにした。150手の探索ではクリア0で、1,000手の実行は中止した。探索器は `COGNITION_EXPLORER=1` のときだけ使う（既定は無効）。目指すのは、VCGT の人間の流れである。仮説を立て、区別できる少数の試行で規則を理解し、ゴールから逆算して計画する。

`scripts/verify_hypothesis_prompting.py`（結果：`outputs/v7-hypothesis-prompting/`）。各ゲームのレベル1の最初の画面から Qwen にゴールの仮説を出させ（温度0.7、各5回）、正解が上位3つに入るかを測った。手数は使わない。VCGT の ls20・vc33・ft09 の注釈は使っていない（答えが漏れるため）。一般的な問いだけを使った。

- C0：今の方式（画像と、物体一覧の ID・範囲）
- C1：画像に物体の ID を書き込む（Set-of-Mark）
- C2：C1 に、VCGT の思考パターンから作った一般的な問いを加える（どれが操作対象・目標・手本・置くべき物か、何がどんな関係になれば成功か）
- C3：C2 に加えて、仮説の前に物体の役割を書かせる

| 設定 | C0 | C1 | C2 | C3 |
|---|---|---|---|---|
| ls20（プレイヤーは未確定） | 0/5 | 0/5 | 0/5 | 0/5 |
| **ls20（方向キーで動く物体を実測で確定）** | 0/5 | 0/5 | **3/5（3回とも1位）** | **5/5（5回とも1位）** |
| vc33 | 0/5 | 0/5 | 0/5 | 0/5 |
| ft09 | 0/5 | 0/5 | 0/5 | 0/5 |
| vc33（クリックの効果の実測を渡す） | 1/5 | 0/5 | 0/5 | 0/5 |
| ft09（クリックの効果の実測を渡す） | 0/5 | 3/5（1位2回） | 0/5 | 0/5 |

分かったこと：

- **実測の事実と、役割を考えさせる問いの組み合わせが決定的だった（ls20）。** 「方向キーで動く物体はこれ」という、数手で測れる事実を渡し、役割を書かせてから仮説を出させると、正しいゴール（プレイヤーを上部の枠へ入れる）が5回とも1位に出た。どちらか一方だけでは0。画像に ID を書き込むだけでも効果はなかった。これは VCGT の人間の流れ（少し試して何が動かせるかを確かめ、役割を考えてゴールを立てる）と一致する。
- **クリック型では、一貫した改善は見られなかった。** vc33 で Qwen は、実測の効果（ボタンで黄色い印が左へ動く）を渡されても、「黄色い印を白い領域の中に」「青いボタンをピンクのカウンターの中に」など、的外れな組み合わせを出した。述語の `color` 欄に毎回色を書き込むなど、出力の形式の誤用も多い。
- 試行の回数は各5回で、3ゲームだけの結果である。ls20 の差（0/5 → 5/5）ははっきりしているが、クリック型の小さな差（0〜3/5）は、ばらつきの範囲を超えるとは言えない。

実行時の流れへの示唆：

- **仮説を立てる前に、区別できる少数の試行で「何が操作でき、何が起きるか」を確かめる**（方向キーなら各1回、クリックなら目立つ物体を数個）。確かめた事実を、C3 の形（ID の書き込み、一般的な問い、役割を先に書く）で Qwen に渡す。
- クリック型のゴールの推定には、さらに別の手がかりが必要。たとえば「同じ色の物体が別の場所にある」「動く物体が向かいうる先」といった関係を、プログラムが実測から示すことが考えられる。

## 5. 確認の段階・V7 形式の仮説・失敗からの修正を実装した評価（2026-09-30）

- 実装：確認の段階（`_orient_step`）、仮説の工程の V7 化（番号を書き込んだ画像、実測の事実、VCGT 由来の問い、役割を必須の欄として先に書かせる）、達成できる条件から試して失敗の経緯を次の仮説に渡す処理。仮説の物体は同色の連結成分とし、ID を追跡で安定させた。
- 実行時に V7 の効果が再現しなかった原因を、V7 の入力から実行時の入力へ違いを1つずつ加えて特定した（ls20、1マス動いた後の画面、各10回）：V7 の形で 9/10、物体一覧の書き方（色をリストに、`kind` 欄）で 4/10、実測の事実を加えて 10/10。役割の欄を省略できる形にすると、空のまま返り効果が消えた。いずれも修正した。
- V7 の最初の「5/5」は、別の種で10回試すと 5/10 だった（1マス動いた後の画面では 8〜9/10）。
- 評価（3ゲーム×2回、100手・600秒、`20260930T121706128431Z`・`20260930T123841373082Z`）：**クリアは0**。
  - ls20 の最初の仮説は「プレイヤーを左下のパネルに入れる」などで、正解ではなかった。実行時の最初のリクエストをそのまま10回再送すると、正解は 3/10。オフラインの最良の形（9〜10/10）との差は、出力の受け取り方（ツール呼び出しと JSON スキーマ）などの細かな違いに残っている。

分かったこと：**4B の Qwen のゴール仮説は、入力の書き方の小さな違い（色をリストで書くか文字列で書くか、ツール呼び出しか JSON か）で、正解率が 3/10〜10/10 の間で大きく変わる。** プロンプトを3つのゲームに合わせて調整していくと、特定のゲームへの過剰適合になる恐れがある。

## 6. V8：書き方の違いはゲームをまたいだ傾向か（2026-09-30）

`scripts/verify_hypothesis_formats.py`（結果：`outputs/v8-format/`）。同じ内容（番号を書き込んだ画像、VCGT 由来の問い、必須の役割の欄、物体一覧）を5つの書き方で渡し、6ゲームのレベル1の最初の画面で、各10回（温度0.7）測った。ls20 と tu93 には「方向キーで動く物体」を実測済みとして渡した。

- ゲーム：既存の ls20・vc33・ft09 に、r11l（足を動かして胴体を目標に合わせる）、tu93（迷路で青を緑のゴールへ）、ka59（緑のブロックを枠へ）を加えた。
- 正解の基準：ls20・vc33・ft09 はゲームのソースから、新しい3つは最初の画面と VCGT の説明から作った。採点にだけ使う。
- 書き方を選んだ根拠は、Qwen3-VL の技術報告にある学習の形式。物体の位置は 0〜1000 に正規化した座標で学び、空間は物体どうしの相対的な関係として学び、関数呼び出しは根拠を書いてから呼ぶ形で学んでいる。

| ゲーム | F-A 基準（色は文字列、0〜63、JSON で出力） | F-B 色をリスト＋`kind` | F-C 座標を 0〜1000 の `bbox_2d` | F-D ツール呼び出しで受け取る | F-E 考察の欄を先に | F-CE（C＋E） |
|---|---|---|---|---|---|---|
| ls20 | 2/10 | 1/10 | **10/10** | 1/10 | 6/10 | **10/10** |
| tu93 | 8/10 | 9/10 | 4/10 | 0/10 | 9/10 | **10/10** |
| vc33 | 0/10 | 0/10 | 1/10 | 0/10 | 0/10 | 1/10 |
| ft09 | 0/10 | 0/10 | 0/10 | 0/10 | 0/10 | 0/10 |
| r11l | 1/10 | 0/10 | 0/10 | 0/10 | 4/10 | 1/10 |
| ka59 | 0/10 | 0/10 | **8/10** | 0/10 | 0/10 | 0/10 |
| 合計 | 11/60 | 10/60 | **23/60** | **1/60** | 19/60 | 22/60 |

分かったこと：

1. **ツール呼び出しで仮説を受け取ると、ゲームをまたいで大きく悪化する（1/60）**。これは6ゲームすべてで一貫した、最も強い傾向である。実行時の仮説の工程はツール呼び出しで受け取っているので、V7 の効果が再現しなかった主な原因だと考えられる。
2. **座標を学習時と同じ 0〜1000 の形式にすると、合計は約2倍になった**（11 → 23/60）。ただし tu93 では下がるなど、ゲームによって差がある。
3. **考察の欄を先に置くと、合計はやや良くなった**（19/60）。F-C と組み合わせると、移動のゲーム（ls20・tu93）では10/10になった一方、ka59 では0に下がった。組み合わせの効果はゲームによって違う。
4. 色をリストにする書き方（H1）には、一般的な差はなかった。§5 で見た ls20 での差は、ばらつきだったと考えられる。
5. **操作できる物体を実測で渡した移動のゲームは、良い書き方ならほぼ確実に正解が出る。** 一方、クリックのゲーム（vc33・ft09・r11l）は、どの書き方でも低い。クリックで何が起きるかという実測の手がかりが、まだ足りない。

実行時への示唆：

- 仮説の工程は、ツール呼び出しではなく JSON スキーマでの出力（`response_format`）で受け取る。
- 物体の位置は、0〜1000 の `bbox_2d` で渡す。
- 1回の結果は、書き方やゲームによって正解率が0〜100%とばらつく。複数回抽出して、繰り返し出る仮説を優先する（合意済みの方針）ことで、ばらつきを平均化する。

## 7. V9：クリックの確認の方法と、6ゲームでの評価（2026-09-30〜10-01）

|---|---:|---:|---:|---:|---:|
| プログラムの目立ちやすさの順（珍しい色・小さい物体から） | 4 | 53 | 1 | 2 | 60 |
| Qwen が「押せそうな物体」を順位付け（各5回） | 2〜5 | 上位6つに入らず | 1〜2 | 2〜3 | — |

手がかりのない最初の画面では、試したどの決め打ちもランダムより遠回りだった。ft09 では、同じ見た目の青いマスでも効果があるのは右下の領域だけだった。確認の段階のクリックは、ステータスバーと背景を除いてランダムな順にし、効果が見つかった時点で止める（最大6回）。方向キーは、動く物体が見つかった後も4方向を1回ずつ試す。

### 実装

- 仮説の工程を、ツール呼び出しから JSON スキーマでの出力（`response_format`）に変えた。物体の位置は 0〜1000 の `bbox_2d` で渡し、考察の欄を最初に置く。3回抽出して、繰り返し出た仮説を優先する。全回が不正なら、誤りを伝えて1回だけ呼び直す。
- 確認の段階を上記のとおり変えた。

## 8. 新しい事実がないときは聞き直さない（A）・条件ごとの評価（B）（2026-10-01）

### §7 の評価で見つかった問題

- **聞き直しで時間を使い切る**：仮説の工程を1ゲーム19〜22回（各3回抽出、1回約28秒）呼び、600秒の約9割を使った。仮説は0〜1手で捨てられ、新しい事実がなくてもすぐ聞き直していた。
- **正しい条件が道連れになる**：1つの仮説に「同じ色」「同じ形」など計画できない条件が混ざり、仮説全体が「計画が立たない」として捨てられていた。
- **tu93：同じ色の壁**：壁と通路が同じ色のため、色で覚える止まり方（`blocking_colors`）では何も学べず、同じ壁へ95回押していた（予測の的中 1/95）。

### 実装

- **位置で覚える壁**（`rules.py` の `stuck`）：学習済みの移動が何も動かさなかったら、「この位置でこの方向は動かない」と記録する。動いたら消す。予測（`predict`）、経路（`plan_path`）、逆算（`Planner._move`）で使う。tu93 の予測の的中は 1/95 → 64/90 になった。
- **A：新しい事実がなければ聞き直さない**（`goal_runtime.py` の `_evidence_key` / `_experiment_step`）
  - 事実の鍵は「動く物体と方向ごとの移動量」「効果のあったクリックの見た目と、それが動かす見た目」「止める色」。同じボタンを別の盤面で押して結果が増えただけでは変わらない。
  - 仮説が尽きても鍵が前回と同じなら、Qwen を呼ばずに試行する。未使用の操作 → 動く物体があれば、まだ訪ねていない一番近い物体へ移動 → 未クリックの見た目をランダムに → 効果のあったクリックのうち試した回数が最も少ないものを今の盤面で押し直す。
  - 試行できなければ代わりの1手を打つ。8手たっても新しい事実がなければ聞き直す。
  - 鍵が変わったら、「計画が立たない」で捨てた仮説から先に試し直す（`hypotheses_retried`）。
- **B：条件ごとの票と評価**：3回の抽出で、条件ごとに「出た抽出の数」を数え、上位6条件をそれぞれ1条件のゴールにする。計画できるゴールを先に進める。達成してもクリアしなかった条件は `achieved` に残し、以後の計画ではその条件を保ったまま次の条件を狙う（複数条件がそろってクリアになる場合のため）。
- **試走で見つけて直したこと**
  - 仮説の直後に全部捨てると、試行せず代わりの1手で終わっていた。
  - クリックの規則が、再び起きた結果を最新として扱わず、古い結果（ft09：一度だけの色の変化）で予測し続け、同じ1手の計画を30回押していた。
  - 代わりの1手が、物体の番号がフレームごとに変わるため、ステータスバーを「一番試していない物」として押し続けていた（ka59：82回中61回）。カウンターとステータスバーを除き、見た目ごとの回数で選ぶようにした。

## 10. クリックの規則を物体ごとに覚え、逆向きの対をスキルにする（2026-10-01）

### 原因

- vc33 には同じ見た目の青いボタンが2つあり、o7 は黄色い印を左へ4、o3 は右へ4動かす。規則を見た目（色と形）ごとに覚えていたため、o7 で学んだ「左へ4」を o3 にも当てはめて計画し、結果が食い違った。規則は「盤面しだいで変わる」扱いになり、逆算計画はボタンを使えなくなった。最初の仮説生成で出ていた正解（`same_column`）も「計画が立たない」で捨てられた。
- ft09 も同じ構造で、同じ見た目の青いマスでも反応するのは一部の場所だけ（V9）。見た目ごとに「押した」と記録していたため、他の場所のマスを試さなかった。

### 実装

- **規則（事実）**：クリックの結果を、見た目ごとに加えて、その場所の物体ごと（`click_at`）にも記録する。予測と逆算は `click_rule` を使う。その物体自身の記録を優先し、見た目での一般化は、その見た目の物体がすべて同じ効果だったときだけ行う（`position_dependent`）。
- **スキル・ノウハウ**（ユーザーの提案）：
  - 同じ物を逆向きに動かす物体の対を規則から見つけ（`inverse_pairs`）、`opposite-…-controls` スキルにする。
  - 仮説を出すときの事実にも「o3 と o8 は逆向きの操作」と入れる。
  - レベルをクリアしたとき、対があれば「同じ見た目のボタンは逆向きの対になることがある」をノウハウとして次のレベルへ持ち越す（`knowhow`）。
- **行動**：
  - 確認の段階で効果のあるクリックが見つかったら、同じ見た目でまだ押していない物体（双子）を1つ押し、対かどうかを確かめる。
  - 未クリックかどうかの判定も物体ごとにした。
