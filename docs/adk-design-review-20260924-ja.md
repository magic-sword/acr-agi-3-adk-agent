# ADK 2.0 スキル・状態機械の設計再確認

確認日: 2026-09-24。以下は再設計前のレビュー記録。対応後の現行仕様は[スキル接続と責務](adk-native-skills-ja.md)を参照。対象はレビュー時の作業ツリー、同梱・実行中の `google-adk==2.0.0`、Google公式資料と公式リポジトリ。今回は設計レビューであり、実行コード・スキル本文の変更は行っていない。

**判定: 状態機械の基本構造はADK 2.0に沿っている。一方、スキルの分類・内容には状態の指示やホスト制御との混同が残る。「15個の認知能力を実装済み」と評価できる状態ではない。**

指示文だけでもADKのSkillとして成立する。公式仕様で必須なのは `SKILL.md` で、スクリプトは任意である。問題はPythonコードの本数ではなく、ロードしたときに共通指示以上の再利用可能な手順・知識が得られるか、公開した実行機能が接続されているかである。[公式Skills仕様](https://adk.dev/skills/)

## 責務の境界

|層|担当するもの|このプロジェクトでの例|
|---|---|---|
|Workflow / 関数ノード|実行順序、分岐、再試行、予算、検証、確定|VERIFYの後にUPDATE、必要時にREVISE、COMMITで確定|
|Agent instruction|その状態で必ず果たす役割と提出契約|PROBEは識別実験を提出、VERIFYはInterpretationを提出|
|Session state / 型付きデータ|実行ごとに変わる事実・仮説・計画・進捗|`Memory`、`pending`、`goal`、`memory_revision`|
|Skill|必要時に読む、再利用できる専門手順・知識と任意の資料・実装|遮蔽中の対象を再同定する方法、介在操作を考慮した因果診断|
|Tool|型付きの呼び出しで実際に処理を行う機能|観測比較、カーソル移動、検証付き提出|

この区分は公式APIの役割を本プロジェクトに当てはめたレビュー上の整理。ADKが特定のファイル分割やスキル数を要求しているわけではない。[Graph workflows](https://adk.dev/graphs/)、[Data handling](https://adk.dev/graphs/data-handling/)

## 修正すべき点

### 1. スキルの多くが専門手順ではなく短い責務の再記述になっている

15定義のうち、S02/S04/S06/S07/S08/S09/S10/S11/S13/S14/S15の11定義は、共通の5項目のうち2項目目だけが固有の指示になっている。たとえば [S08](../agent/skills/backward-planning/SKILL.md) は「目標から逆算し、前提・維持条件などを含める」と書くが、逆算の進め方、分岐の判断、打ち切り条件、失敗例は具体化されていない。

全15個の `references/evidence-contract.md` はバイト単位で同一だった。共通契約の複製は、各技能固有のL3資料が存在することの証拠にはならない。S01/S12には具体的なツール利用手順と実装があり、S03/S05にも追加の説明があるため、全スキルが同じ程度に空疎という評価ではない。

対応案: 各スキルに適用条件、判断手順、必要な証拠、結果の品質基準、失敗時の扱い、具体例を持たせる。計算・検査が必要な部分だけToolやスクリプトにする。これは品質改善案であり、スクリプト追加をADKの必須条件にしない。

### 2. ホストの必須制御がスキルの分類に混ざっている

旧S13 `decision-commit` は `SKILL_NAMES` に存在するが、どのモデル状態の `STATE_SKILLS` にも登録されない。実際の確定は [engine.py](../agent/cognition/engine.py) の `commit()` と [workflow.py](../agent/cognition/workflow.py) のCOMMITが行う。ホスト実装は存在するので機能欠落ではないが、実行するSkillと同列に数える分類が不正確である。

旧S15 `budget-recovery` の内容も予算遵守と停止が中心。予算の強制はホストの責務であり、任意ロードの有無に依存してはならない。現状はホストにも上限処理があるため、制御がスキルだけに任されているわけではない。

対応案: S13はホストの確定契約として整理する。S15の必須制約はホストと共通instructionに置く。予算内で実験の価値を比較する固有の判断手順を持たせる場合に限り、その部分をSkillとして独立させる。状態エージェント名 `skill_plan` 等も、役割を表す名前にすると区分が明確になる。

### 3. 公開されたスクリプト実行ツールが実行基盤に接続されていない

[skills.py](../agent/cognition/skills.py) の `SkillToolset` と [workflow.py](../agent/cognition/workflow.py) の `LlmAgent` は、どちらも `code_executor` 未設定。それでも標準の `run_skill_script` はモデルに公開される。

実行環境のADK 2.0.0で、PLANのtoolsetから `action-grounding/scripts/controls.py` を指定して呼び出すと、`error_code=NO_CODE_EXECUTOR` が返ることを確認した。公式2.0.0実装も、toolsetとagentの両方にexecutorがなければこのエラーを返す。[公式実装](https://github.com/google/adk-python/blob/v2.0.0/src/google/adk/tools/skill_toolset.py)

ただし、2個のPythonファイルが未使用という意味ではない。`agent/controls.py` と `agent/observation.py` がスキル配下の実装を通常のPythonモジュールとしてimportし、ホスト処理に利用している。**ホストからの実装利用と、モデルからのSkillスクリプト実行は別経路**である。

対応案: 現在の用途なら、既存の型付きToolを実行窓口にして、未接続のスクリプト実行機能の公開を整理する。スクリプトをモデルから使う要件がある場合は、executor・依存関係・入出力を整備して個別に検証する。executorを追加するだけでは、リポジトリ内importやCLIを持たないモジュールの問題まで解決しない。

### 4. 段階的ロードが判断予算を圧迫している

[instruction()](../agent/cognition/skills.py) は、状態別の課題と多数の共通規則を既に渡したうえで、各判断に `list_skills` → `load_skill` を指示する。`include_contents="none"` により、以前の判断でロードした本文が次の判断にそのまま引き継がれる構成でもない。

保存済みの [12:39 UTCのモデルログ](../outputs/evaluations/20260924T123912417412Z/ls20-9607627b/cognition/c24fb7ae24f145829935d90e47fded9e.model.jsonl) では、PLANとPROBEがそれぞれ8 HTTP要求を使い切っている。PLANは一覧・本文2件・共通参照の計4要求、PROBEは一覧・本文3件の計4要求を使っていた。「最大2スキル」は指示であり、PROBEで3件ロードした事実からも強制上限ではない。

これらは過去の測定であり、今回の性能再評価ではない。またロードだけが停止の原因と断定できない。ただし、専門的な情報が増えない読み込みに予算を使う構成は改善対象になる。

対応案: 必須契約はinstructionと検証に集約し、Skillは追加の専門知識が必要な場合に選択する。共通資料の重複ロードを減らす。制約を必ず守る必要があるならコード側で管理する。変更の効果は同一モデル・同一予算で比較する。

## 状態機械についての判定

`Workflow(edges=...)`、`Event(route=...)`、関数ノードからの `ctx.run_node(agent, node_input=...)`、親ノードの `rerun_on_resume=True` は公式のグラフ・動的ワークフローの利用方法に合う。LLMに提案させ、コードで検証・遷移する構成を置き換える必要はない。[公式Dynamic workflows](https://adk.dev/graphs/dynamic/)

確定済み認知記憶はCOMMITの `Event(state={"cognition": ...})` で公開し、次の判断に戻している。`Memory` と指示文も別に定義されている。したがって、状態データとプロンプトが実装全体で一体化している、という指摘には当たらない。

一方、ノード間の作業データは `self.turn`、提出結果は `self._submission`、画像証拠は `self.evidence` にあり、ADKのノード入出力やSession stateだけから復元できない。`ctx.run_node` の返り値も提出結果としては使っていない。現状の単一プロセス・直列実行では成立するが、ADKの再開機能を有効にするだけでプロセス障害から復帰できる設計ではない。既存ドキュメントも診断用スナップショットからの自動復元を保証していない。

再開・並列化が要件になったら、判断単位の作業データと提出結果を明示的なノード入出力／状態に載せ、画像は復元可能な参照で扱う。現段階では機能不具合の断定ではなく、利用範囲の制限として扱う。

## 再設計の優先順

1. ホスト制御・状態instruction・Skill・Toolの分類と説明を一致させる。S13/S15とスクリプトの実行経路を先に整理する。
2. 汎用定型文だけのSkillを、具体的な再利用手順として作り直す。S08なら「達成条件→必要な前提→証拠のある操作候補→維持条件と依存関係→次の1手または検証すべき未知」の手順・例・失敗条件を持たせる。
3. 必須指示の重複と不要なロードを減らし、スキル選択・専門手順の有用性を実モデルで評価する。
4. 再開が必要なら、ホストの一時変数に依存するノード間データを整理する。
