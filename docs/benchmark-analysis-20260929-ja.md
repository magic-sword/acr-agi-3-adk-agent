対象：`outputs/evaluations/20260929T132323611961Z/`。ユーザー指定の `/kaggle/working/` 配下と同じ実行IDのローカル保存ログを分析した。

評価に保存された `package/`、manifestのソースハッシュ、現在の対応するソースを照合し、差分がないことを確認した。以下は既存ログ・実画像・実装の分析であり、修正後の再評価ではない。ゲーム内部の正解ルールは参照していない。

## 結論

操作前の計画ループと誤った完了判断により、環境から新しい証拠を得る前に判断時間を使い切っている。さらに対象名と実マスクの対応が崩れており、唯一実行したクリックも意図した対象の有効な検証とは言い切れない。

今回、SAMはCUDAで初回約7秒、高速実行は1回0.39〜0.69秒だった。改善した部品は動いているが、計画から操作へ進む条件と、意味・領域・完了の整合性が不足している。

## 1. 説明をゲーム目標として受け入れ、修正できない

vc33の最初の `goal_hypothesis` は次の内容だった。

> Identify the current state of the game board and its visible components.

`backchain` も同じ文を `desired_state` にし、`intent=achieve`、理由は「既に観察できているので操作不要」。候補生成は空配列を返した。

最初は `missing_info` が空で拒否されるが、修復後は「候補不要、目標は達成済み」という説明を入れるだけで受理される。実際には対象情報が欠けていないのに、空候補を一律に「対象情報不足」として再理解に戻すため、同じ画面で2周した。3回目の理解で時間切れ。

ft09の最終目標も「盤面と次の操作に関係するパターンを把握する」であり、ゲーム内の達成状態になっていない。

実装では、Sceneの目標は文字列の長さだけを制約し、理解の検証は主に参照IDを確認している。`final_goal` は初回にだけ設定され、同一episode内では再理解しても更新されない。最初の誤った仮説が後続計画の前提として固定される。

「最終目標は観測可能なゲームの結果」「未知なら操作して検証する」という指示は、実際に送信したリクエストにも既に存在する。指示文の欠落ではなく、指示に反する出力を意味の面で受け入れる問題である。

該当実装：[focused_state.py](../agent/cognition/focused_state.py) の `Scene`、[focused_workflow.py](../agent/cognition/focused_workflow.py) の `validate_stage`、`_accept_stage`（379〜390、427〜428、477〜510行）。

## 2. achieveでは未操作の完了を選べる

ls20は「白い十字を上の青い対象へ移動する」を選び、移動と位置確認の2手順を生成した。しかし高速実行は同じ初期画面で連続して `7`（完了）を返した。方向操作は1回も送信していない。

実画像では十字は左寄りの中央、青い対象は上側にあり、重なっていない。それでも結果照合は「十字は青い対象の中心にある」「移動した」と説明した。`goal_status=confirmed` はホストが禁止したため `active` に留まったが、再理解へ戻る時間は消費した。

`_think` は `intent=achieve` なら初回から完了選択肢を提示する。probeに追加された「受付＋観測前は完了を選べない」制約は、この経路には適用されない。テスト `test_achieve_offers_completion_without_action` も現状の挙動を明示的に保証している。

既に満たされた手順を飛ばすこと自体は必要だが、それと「今回の操作で達成した」を区別し、観測上の根拠と無操作ループの上限を持つ必要がある。単にすべての手順で操作を強制する対処では不十分。

該当：[focused_workflow.py](../agent/cognition/focused_workflow.py) の704〜705、725〜733行、[test_focused_workflow.py](../tests/test_focused_workflow.py) の245行以降。

## 3. 対象名とマスクが一致していない

これはSAMの生成失敗とは別の、意味と領域の対応付けの問題。

| ゲーム・対象名 | モデルが結び付けた実領域 | 問題 |
|---|---|---|
| ls20「上の青い対象」 | `f1t25` 上の青い図形 ＋ `f1t24` 下端の赤・黄のバー | 離れたUIまで同一対象に合成 |
| ft09「左上の区画」 | `f1t74`〜`f1t77`、座標36〜57付近の右下の青い領域 | 左上という名前と位置が逆 |
| ft09「拡大表示」 | `f1t78` 右下の区画 ＋ `f1t79` 下端のオレンジ線 ＋ `f1t44` 黒い背景 | 画面全体に広がる対象を生成 |

ft09の「拡大表示」は `e1o93`、bbox `[0,0,63,63]` として採用され、ホストは合成マスク内の重心に近い `(33,34)` をクリックした。受付成功、変化画素0。この座標は表示画像の灰色の枠付近であり、中央の白い小対象ではない。

次の理解では「中央の白い対象」にも同じ3領域を指定した。その結果、次の候補「中央の白い対象」と「拡大表示」は両方 `e1o93` になった。言葉上では別の検証でも、実行先が同じになる危険がある。ただし2回目の操作は時間切れで未実行。

`validate_stage('understand')` は存在する参照かどうかを確認するが、名前・色・位置との一致は検証しない。`bind_target` は複数の有効な参照を `interpreted_group` にできる。`click_point` はそのマスクの内部を選ぶため、座標処理が正しくても誤った意味対象をクリックし得る。

該当：[focused_workflow.py](../agent/cognition/focused_workflow.py) の379〜387行、[object_memory.py](../agent/cognition/object_memory.py) の226〜247行、[simple_workflow.py](../agent/cognition/simple_workflow.py) の `click_point`。

## 4. 45秒の予算と計画工程の費用が合っていない

ft09の初回は次の内訳だった。

| 工程 | 時間 |
|---|---:|
| 初回認識（SAM等） | 7.36秒 |
| understand | 16.91秒 |
| backchain | 4.46秒 |
| candidates | 4.25秒 |
| ground | 6.24秒 |
| execute_step | 0.69秒 |
| 判断全体 | 39.93秒 |

初回から残り約5秒しかない。次の判断ではSAMを再実行せず認識は約0.004秒だったが、結果照合4.73秒、再理解18.94秒、小目標5.08秒、候補10.05秒を消費し、手順生成は残り約6.16秒でタイムアウトした。

理解の入力は10,883→12,517トークン。初回だけで87領域を提示し、`measured_objects` の領域表に加えて `object_index` の領域・グループ・包含関係を渡している。後者はJSON換算で初回約12,000文字、2回目約13,300文字。履歴軽量化だけでは、この入力と長い構造化出力の費用は解消しない。

さらに `reconcile` 後は `resume` 以外を実装側で必ず `understand` に戻している。モデルが `ground` や `backchain` を選んでも理解を挟む。ft09ではモデル自体も `understand` を選んでおり、無変化の画像を再び全面的に説明した。

45秒超過は、その判断を一旦中断して再開する扱いではなく、runtime全体を `STOPPED` にする。全体600秒のうち大部分を残して終了する理由はここにある。

該当：[focused_workflow.py](../agent/cognition/focused_workflow.py) の297〜300、590〜600、732〜733行、[execution.py](../agent/cognition/execution.py) の93〜96、194〜196行、[adk_policy.py](../agent/adk_policy.py) の16行。

## 5. テスト成功と今回の失敗は矛盾しない

引き継ぎの241テスト成功は、計画の保持、スキーマ、状態遷移、受付などの実装検証として有効。一方、計画の主要テストはモデル応答を固定しているため、実モデルが出す「説明が目標」「参照は実在するが意味が違う」「初期状態で誤完了」は検証できない。

今回、操作送信経路の故障は確認されていない。唯一の操作はSDKに受理されている。また `candidate_provider_invalid` はこの実行の停止理由ではない。主因をその例外名やCPU SAMの37秒に帰すのは、今回のログとは合わない。

## 改善の優先順位と検証方法

1. **操作に到達できる計画契約を作る。** 最終的なゲーム成果と暫定的な攻略仮説を分け、説明だけの目標、既に満たされた小目標、対象不足を別扱いにする。同じ観測・同じ目的で空候補や未操作完了を繰り返したら、実行可能な検証へ切り替える。仮説の更新経路も必要。
2. **意味対象と操作領域を一致させる。** 候補の色・位置・マスクを画像上で対応確認できる入力を用い、背景・UI・対象を混ぜたグループをそのまま操作先にしない。全体の仮説を保持しつつ、実際に作用させる部品を明示する。異なる名称が同じマスクに対応する場合は、別の実験として扱わない。
3. **再理解の必要性を限定する。** 無変化・同一性維持なら、現在の参照へ更新した対象と直近の結果を使って候補／手順の見直しへ進む。計画を保持する役割は維持し、毎回の全面再生成を避ける。
4. **予算を実測に合わせる。** 初回認識、計画、継続実行に分けて計測する。45秒→100〜120秒の比較は時間不足の切り分けには有効だが、無操作ループと誤認識の修正にはならない。時間切れ時に継続可能な状態を残す設計も検討する。
5. **実モデルの行動回帰評価を追加する。** この3初期画面と実応答を固定ケースにし、初回実行までの時間、無操作での計画反復数、意味対象と領域の一致、1回の計画から実行できた操作数、結果照合から次の操作までの時間を測る。操作数だけでなく、未検証の関係を判別する情報が得られたか、到達レベルが増えたかも確認する。

まず操作前ループと対象対応を直し、その後に同じ制限で再評価するのが妥当。現状の1操作・0レベルから、攻略戦略全体の良否やSAM方式の優劣までは評価できない。
