# スキル責務の再設計と検証

> 過去の実装・調査の記録です。現在の仕様・実行コマンドは[現行実装](../skill-learning-runtime-ja.md)を参照してください。旧APIと旧比較コマンドは削除済みです。

更新日: 2026-09-24。[設計レビュー](adk-design-review-20260924-ja.md)を受けて実装を変更した。現在の構成は[接続仕様](../skill-learning-runtime-ja.md)と[13スキルの責務](../skill-learning-runtime-ja.md)を参照。

## 実装の変更

- 状態の必須指示を `agent/cognition/instructions.py` へ分離。状態エージェントの名前を `reasoner_*` に変更した。
- 確定と予算制御（旧S13/S15）をホスト責務として分類し、SKILL.mdと登録を削除した。
- 残る13スキルを、具体的な判断手順、適用条件、反例、不確実な場合の扱いを持つ専門手順に書き直した。
- 同一内容だった15個の共通参照資料を削除し、必要な4スキルに固有の補足例を置いた。
- `ReasoningSkillToolset` でADK標準の本文・資料ロードを使用。L1は初回から提示し、一覧取得のHTTP往復と毎回の必須ロードを廃止した。
- 未接続の `run_skill_script` を公開しない。実行スクリプトや動的ツールを宣言した知識パッケージは構築時に拒否する。
- 描画と操作変換は `agent/rendering.py` と `agent/controls.py` へ移した。観測・完了ツールはスキルのロードに依存せず使える。
- 設計資料、ソースから生成する構成図、Kaggleノートブックを更新した。

Workflowのグラフ・検証・予算・確定処理は維持した。障害後の再開は今回追加していない。状態機械の実行中データと証拠ストアを復元する設計は、再開が要件になったときの別作業である。

## 自動検証と接続確認

`docker compose run --rm --no-deps dev python -m unittest discover -s tests -v` で **85件成功**。操作順検査の5テストを含む。構成図の関連3テストも確認した。

主な確認対象は、ADK実経路でのL1提示とL2/L3の遅延ロード、非公開ツールの除外、状態外のスキルの拒否、未接続実行機能の構築時拒否、ロードなしでの完了ツール受理、既存の証拠・予算・操作・記憶の契約。全13スキルはスキル形式検証を通過し、資料リンクも確認した。描画CLIと移動後のホストimportは回帰テストに含まれる。

`python scripts/check_skills.py` の実モデル確認は、本文→参照資料→回答の **3 HTTP要求** で成功。ランダムな検証値が参照資料だけに存在するため、モデルが実際のツール結果を読めたことを確認できる。

[接続ログ](../../outputs/skill-checks/dd11f4bbc42a4f3aa83a9ebed4645e92/result.json)。スキル数や読み込み成功を攻略能力の実証には用いない。

全件が `proposal_unavailable` で終了。実験提出と1操作を確認したが、レベルクリアや攻略性能の改善は確認できなかった。vc33/ft09では操作後のVERIFY提出も受理された。ft09のセル値型違反と根拠欠落は、完了ツールが拒否し、モデルが同じ判断内で訂正した。

初回PLANではスキルを読まず、同じ観測の再取得や自己比較を繰り返す場面が残った。新しい構成で一覧取得の往復はなくなったが、余った予算が必ず有用な推論に使われるとは限らない。

直前のls20測定は3操作上限、今回の3ゲーム測定は12操作上限なので、完全に同条件の性能比較とはしない。過去の12操作上限の3ゲーム測定とも完了プロトコル等が異なり、スキル変更単独の因果効果は主張しない。

## 専門手順の小規模評価

`python scripts/check_reasoning_skills.py` で、指定したスキルを読んで文章の場面から選択肢を選ぶ確認を追加した。各例は最大4 HTTP要求・60秒、実ゲーム操作なし。モデルには正答を渡さず、返されたchoiceとロード履歴を検査する。これは画像認識や自主的なスキル選択を測定するものではない。

初回は遮蔽・実験設計・逆算計画・計画修復の4例中3例が正答。逆算計画では、ブロックを先に置くとスイッチへの経路がなくなるという前提を無視した。[初回ログ](../../outputs/skill-checks/methods-12d9f1ff95c746a98229f150370b8e2d/result.json)。

この結果に基づきS08へ、候補順序を前から検証して「各操作が必要とする条件」と「前の操作が削除する条件」を照合する手順を追加した。元の4例に、逆順が必要な例と両順序とも成立しない例を加えて再評価した。

上表の3ゲーム測定はこのS08の追加修正・操作順チェックツールの追加より前のスナップショットである。その測定中にS08はロードされていないが、最終スキル一式での攻略性能を測った結果とは区別する。

文章のみを補強した再評価は6例中5例が正答で、元の逆算計画例は再び誤答だった。[再評価ログ](../../outputs/skill-checks/methods-0d0a3b50c1a142fc891c4eab30b0296d/result.json)。そこで `agent/cognition/planning.py` に、明示された条件の追加・削除を順に適用する `check_plan_order` を実装した。PLAN／REVISEへ直接公開し、S08から必要時に使う。誤った前提を与えれば結果も誤るため、ゲーム効果の根拠にはしない。

操作順ツールの追加後も、最初の[評価](../../outputs/skill-checks/methods-936a8b8211334269b2149e75e96cabab/result.json)ではモデルが検査を呼ばず、指定外の文章形式で回答する例があった。S08を短いツール入力例を含む手順へ整理した最終評価も **6例中3例成功**。[最終評価ログ](../../outputs/skill-checks/methods-2b3a80e2797d4623aa233d0922e7c204/result.json)。

|場面|最終評価|
|---|---|
|隠れたトークンの状態|正答・スキルロード確認|
|区別できない実験と安全な移動後の実験|正答・スキルロード確認|
|アクセスを維持する逆算計画|不成功。JSON契約外の回答、検査ツール未使用|
|残り計画の置換|正答・スキルロード確認|
|逆の操作順が必要な場面|不成功。実在するホストツールを存在しないと回答|
|両順序が前提を壊す場面|選択肢は正答だが検査ツール未使用のため不成功|

逆算計画の3例は、スキルのロード・正しい選択肢・検査ツールの利用をすべて成功条件にした。モデルの理由説明の正しさまで自動保証する判定ではない。ホストツール自体は前提の消失、逆順、相互遮断、最終条件の喪失、不正入力、ADK経由の結果返却をテスト済みである。ツールの実装成功と、Qwenが適切に利用できることは区別する。

この結果を踏まえ、逆算計画の意味解釈とツール利用、不要な証拠再取得、時間予算内の提出が残る能力課題である。今回の責務分離だけで解決済みとは扱わない。


## 最終ソースでのゲーム接続確認

操作順チェックと最終S08を含むソースで、ls20を12操作／1レベル／判断90秒／プロセス110秒の上限で再実行した。[最終測定](../../outputs/evaluations/20260924T133928514521Z/report.md)。manifestの全同梱ソースハッシュは現在のソースと一致する。

結果は **1操作、0クリア、SDKスコア0.0**。PLANは1 HTTP要求で探索依頼、PROBEは5要求で実験を提出し、外部操作を実行した。その後VERIFYで提出の訂正を繰り返して時間切れとなり、`budget_exhausted` で終了した。合計12 HTTP要求、スキル本文ロード2回、一覧取得0回。実測99.4秒には判断時間以外の処理・終了処理も含む。

最終構成でも実操作までの接続は確認できたが、安定した結果解釈と攻略性能は未実証である。操作順チェックはこのゲーム試行では呼ばれていないため、実ゲーム内で活用できたとは主張しない。
