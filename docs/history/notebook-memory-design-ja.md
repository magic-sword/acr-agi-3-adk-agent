## 判断

攻略ノートを通常判断とスキル作成の共通の参照先にする案を推奨する。必要なページだけを読み出せるため、全履歴を毎回渡す方式を避けられる。ただし共有先が一つでも、古い版の読み出し、読み落とし、誤った記述は起こり得る。一貫性と入力の縮小は、保存・参照・更新の仕組みで支える。

スキルはノートの使い方を教える。実際の内容は、全ての仕事から同じツールでアクセスできる永続ストアへ保存する。実行中の経験でSKILL.md自体を書き換える構成にはしない。Jupyter notebookはこのストアと操作履歴を表示する閲覧側として位置付ける。

## 参考文献と借りる仕組み

|資料|論文での構成|本提案への対応|
|---|---|---|
|MemGPT（2023、参照版v2）|限られた主コンテキストと外部記憶を分け、関数呼び出しで読み書きする。主コンテキストには小さな編集可能領域を置き、検索結果にはページ分割を使う|現在開いている短いページと、必要時に開く詳細ページ|
|A-Mem（2025、参照版v1）|一件ごとのノートに時刻・キーワード・タグ・文脈・関連ノートへのリンクを付ける。新しい経験で関連ノートの属性を更新し、検索で必要な記憶を選ぶ|一つの論点につき一枚のノート、しおり・根拠リンク、仮説の改訂|
|Generative Agents（2023、参照版v2）|経験をmemory streamへ保存し、新しさ・重要性・関連性から検索する。内省には根拠とした記憶への参照を保存する|観測と解釈の区別、仮説から元の経験への参照、仕事に応じた選択的な読み出し|

一次資料：[MemGPT §2](https://arxiv.org/html/2310.08560v2)、[A-Mem §3](https://arxiv.org/html/2502.12110v1)、[Generative Agents §4.1–4.2](https://arxiv.org/html/2304.03442v2)。

MemGPTの主な評価は会話・文書処理、参照したA-Memの評価は会話記憶に関する質問応答、Generative Agentsは社会的な振る舞いのシミュレーションである。本プロジェクトの未知の視覚パズルやローカルモデルでの改善を保証する結果ではない。

これらの論文が「ノート・ペン・消しゴム・しおり」という同一APIを採用しているわけではない。また、自由なノートの改訂と、監査用の履歴保存を両立させる以下の設計は、本プロジェクトへの適用案である。

## 四つの機能

|比喩|操作|初期実装の範囲|
|---|---|---|
|ノートを開く|ページID・しおり・検索条件で読む|目標、仮説、実験、観測への参照を必要な件数だけ返す。長いページと検索結果は上限付きで分割|
|ペン|作成・改訂|目標・計画・予測・解釈を書き、観測や他のノートを根拠として関連付ける|
|消しゴム|撤回・退役|誤った仮説を撤回し、通常の表示から外す。以前の版と撤回理由は記録として残す|
|しおり|名前を付けて参照する|現在の目標、進行中の実験、スキル化したい経験などを指す。本文の複製を増やさない|

一枚の巨大な自由文を毎回書き直さず、一つの論点を一枚にする。最低限、ID、種類、本文、版、状態、対象ゲーム・実行・レベル等の範囲、根拠IDを保持する。種類は当初、目標・仮説・計画・解釈程度に抑える。観測の原本には別途、実際の操作・受付結果・前後の画像ID・測定値を保持する。

## 事実と解釈を同じノートから区別して参照する

実際に送った操作、環境からの受付結果、前後の画面、機械的に計測した変化はホストが自動記録する。モデルが手書きした内容だけを実行結果の原本にはしない。たとえば「色の数が変わった」は測定値、「扉が開いた」「UPで必ず開く」は意味の解釈や作用仮説として扱う。

モデルは原本への参照を使って注釈・仮説を書き、後から撤回できる。実行記録の修正が必要な場合も訂正を追記する。消しゴムで原本や過去の版を消すと、失敗の分析や当時の状態の再生ができなくなる。

利用者が与えた目的と、モデルが選んだ部分目標・推定したゲームの勝利条件も区別する。仮説を目標ページへ書いただけで、外部から与えられた確定条件として扱わない。

ノートに「スキルは成功した」と書いてもライブラリの採用状態は変わらない。スキル作成は根拠となる実経験を参照し、採用は既存の固定評価を通す。

## 開いているページと詳細ページ

各仕事の開始時に、ホストが同じノートから小さな開始用ビューを組み立てる。

- 現在の目標の短い本文と版。
- 最新の観測ID、実際の直前操作と結果の短い記録。
- 少数のしおりの名前・参照先と、必要な予算情報。

これは別の自由文要約を毎回生成する処理ではなく、ノートの指定項目からの読み出しにする。通常判断には現在のゲーム画面も渡す。スキル作成には選ばれた経験の画像やグリッドを渡す。過去ノートが現在の画面を上書きしないよう、観測時点を明示する。

詳細な経験・別仮説・手続きの説明は必要時に開く。「ノートを読め」という一文だけで開始すると、何を読めばよいか判断する材料がなく、重要ページを読み忘れる可能性があるため、この小さな開始用ビューを推奨する。毎回同じ目標を読むだけの追加LLM呼び出しも避けられる。

短い共通指示の例：

> 現在の目標と最新結果は開いているページを参照する。必要な根拠はしおりから読む。解釈の変更は根拠付きでノートに記録し、今回の仕事を一つ進める。

実際には、この案内に今回担当する仕事と、その仕事で利用できるツールの契約を添える。ツールの使い方まで一文で暗黙に伝わるとは考えない。

## 一貫した更新とコンテキストの管理

全ての仕事は同一のストアを参照し、独立した目標・要約のコピーを更新しない。移行時は現在のMemory.task / summary / hypothesesとノートを両方の正本にせず、ノートへの参照または読み出しで生成するビューへ置き換える。SkillLibraryの経験原本は複製せず、ノートから参照する。

読み出しにはノートの版と観測時点を付ける。更新は読んだ版に対して行い、古い版に基づく上書きを検出する。初期構成は直列でよく、このために並列エージェントを導入する必要はない。

しおりの有無だけで文脈汚染を防げるわけではない。検索・ページ本文・しおり一覧の返却量を制限し、次の仕事の入力は開始用ビューと選んだページから組み直す。読み出した全ページを会話履歴へ無制限に積み上げない。撤回した仮説は通常の選択対象から外すが、関連する反証や撤回理由は確認できるようにする。

最初は名前付きしおり、ID参照、対象範囲による絞り込み、簡単な文字検索で始める。A-Memのような埋め込み検索やLLMによるリンク自動生成は、検索漏れが問題になってから比較する。毎操作でノート整理専用のLLMを呼ぶ構成は初期案に含めない。

## 再生と比較実験

将来生成するログに、ノートの作成・改訂・撤回、しおりの変更、各仕事が読んだページIDと版、実際に提示した内容を残す。Jupyterの再生では、ゲーム画面と操作に加えて「その時点で開いていたページ」「変更前後」を表示する。現在のノート本文を古い実行時点に重ねて表示しない。既存ログの変換・互換対応はこの案の対象外。

記録するのは目標、根拠、短い仮説・予測、参照と改訂、実結果であり、モデル内部の思考を完全に取得するという意味ではない。

比較は、プロンプト分離の変更と一度に混ぜず、同一のプロンプト構成に対して現行記憶とノート記憶を比べる。モデル、ゲーム、初期スキル、生成設定、操作・HTTP・時間予算、採用条件を揃える。ノート読み書きに必要な呼び出しも予算へ含める。

クリア・進捗、同じ失敗の反復に加え、古い目標や結果への依存、根拠のない記述、関連する反証の検索漏れ、記憶操作の呼び出し数と時間、モデルへ渡した量を確認する。保存量が多いことやノートが詳しいこと自体を改善と評価しない。

## 実装した範囲と変更の経緯

ノートで一貫した記憶を共有する方針が承認されたため、提案を実装した。従来はMemoryのtask・summary・hypothesesと、スキルライブラリの経験が別の入口にあり、通常判断の指示にもスキル作成の手順が常駐していた。

- `agent/cognition/notebook.py`を共有記憶の正本にした。旧MemoryPatchとMemory内の目標・要約・仮説を削除し、目標を`goal`ページへ集約した。
- `read_notebook / write_note / erase_note / set_bookmark`をADKツールとして接続し、`agent/skills/notebook/SKILL.md`に専門的な利用方法をまとめた。本文は必要時にロードできる。
- 各呼び出しには目標ページ、最新のホスト記録、最大8個のしおり（固定2＋任意6）を自動提示する。索引は6件ずつ、本文は目標400文字、その他の手書きノート1000文字まで。検索は文字検索で、埋め込みモデルは追加していない。
- 根拠として実在する観測ID・経験ID・ノートIDを参照できる。ノートを参照した解釈も確定事実にはならない。スキル作成の入口`learn`は、保持中かつ受付済みの経験IDを別途検証する。
- 更新には読んだ版が必要。結果の原本はホストだけが作成し、消しゴムはノートの撤回を記録する。レベル・リセット境界で局所目標としおりを初期化し、以前のノートは明示参照できる。
- `DECIDE / RUN`は維持し、仕事を`action / skill_creation`に分けた。同じモデルを直列に呼び、両方から同一のノートを使う。`learn`を選んだ後の呼び出しだけにskill-creator本文とpropose_skillの詳細Schemaを渡す。証拠不足なら作成役も追加実験の操作を返せる。
- 受付済み経験の参照は通常操作にも付けられる。試験・採用の固定基準や予算は変更していない。
- ログ有効時は`<run>/notebook/<page>-v<revision>.json`に版を保存し、`<run>.notebook.jsonl`に変更前後・参照・しおり・開始時の入力ページを保存する。
- Jupyter再生へ「攻略ノート（入力・参照・変更）」を追加した。パネルを開いたときだけ詳細を描画し、ログの表示位置より未来の改訂を混ぜない。静的HTMLレポートと評価集計にもノートを接続した。

古いログの変換、ゲーム途中からの再起動・復元、ノートのゲーム間自動共有は実装していない。ログ無効時は実行中のメモリ内だけで保持する。採用済み実行スキルの明示的な移植は従来どおり利用できる。

## 検証記録

ADK経由のテストでは、ノートの作成→しおり→参照→操作、次の判断と作成役への目標の継承、古い版の拒否、原本改変の拒否、根拠IDの検証、撤回後の検索除外、境界処理、返却量、当時の版の再生を確認する。既存のスキル作成→実試行→採用→再利用の結合テストも維持した。

最終確認：`python -m unittest discover -s tests -v`は63件すべて成功。Jupyterカーネルでも`agent_observatory.ipynb`を実行し、下記の新しい実走ログを読み込んで攻略ノートパネルを開けることを確認した。実行済みノートブックと結果は`outputs/notebook-memory-validation/`へ保存した。ブラウザでの目視操作はこの検証に含まない。

実モデルの最初の短時間評価（`outputs/evaluations/20260925T101738215271Z`）では、通常操作に経験IDを添えた回答を新しい契約が拒否し、訂正が進まず呼び出し上限に達した。また、初期画面の観測IDを根拠にしたノートを受け付けられなかった。前者は任意の正当な経験参照として受け付け、後者は記録済み観測も根拠として扱うよう修正した。採用判定を緩める修正ではない。
