# 行動計画の工程を減らす比較検証

> 履歴資料。現在の採用方針は[行動計画の統合資料](../../planning-adopted-ja.md)を参照。本文の「次に検証する」は実験当時の提案であり、現在の作業予定ではない。

2026-09-29。[改善提案](planning-causal-next-steps-20260929-ja.md)と[計画・遷移の不整合修正](ground-routing-trial-20260929-ja.md)を踏まえ、現行工程Aと「一操作の計画＋別工程での結果照合」Bを実モデルで比較した。

**Bは初手と呼出し数を改善したが、計画・照合の精度向上は確認できなかった。次に直す中心は、対象・事前予測・実操作・観測結果を同じ試行に結び付ける部分。** どちらもレベル達成は0。現段階でステートの一括削除を通常設定へ採用する根拠はない。

追記：この後、Bの工程を両条件で固定して[観測・試行・知識の分離を比較した](memory-separation-comparison-20260929-ja.md)。古い候補参照の拒否は減ったが、予測を観測事実として説明する問題と、反証を次の行動へ反映しない問題が残った。

## 比較した構成

| 項目 | A：現行工程＋共通入力整理 | B：一操作計画＋結果照合 |
|---|---|---|
| 状況理解・概念化 | 独立した`understand` | 必要な対象と暫定的役割を計画内で解釈 |
| 前提条件の逆算 | `backchain`へ分岐可能 | 計画内で必要な条件を検討 |
| 計画 | 既存の`ground` | 一つの問い・対象・操作・可視効果の予測 |
| 意味質問 | `answer_question` | 独立呼出しを省き、結果照合へ統合 |
| 結果照合 | 既存の`reconcile` | 別のモデル呼出しで支持・不支持・不明を返す |
| 記憶 | `read_memory`でモデルが選択 | 直近3件の実操作結果と直前照合を直接提示 |
| スキル選択 | モデルが選択 | 計画済みの一手をホストが選択 |
| 実行・照準・受付 | 共通の既存機構 | 同左 |

共通の認識は初回SAM＋通常の画素追跡。両方へ前後画像と物体・移動測定を渡す。Bでも結果照合を独立させており、計画だけに全部を担当させる構成ではない。また、今回は**工程の比較であり、画像を省いて測定値だけにする比較ではない**。

Aにも比較用の入力整理を加えた。熟考工程で全候補索引を参照可能にし、同じ要求内の重複した測定辞書を参照表へまとめ、画像提示を直前／現在で統一した。元の測定ログは保存する。したがってAは、無変更の通常設定との同一条件ベースラインではない。この共通変更自体の効果も切り分けていない。

Bの内部では既存の実行・照準・受付・停止処理を再利用する。比較で取り除いたのは独立した推論呼出しであり、状態管理全体ではない。複数工程、記憶提示、出力契約をまとめて変えた比較なので、個々のステートの有害性は特定できない。

## 精度について実際に分かったこと

受理された全23照合を、生の前後グリッド、事前予測、操作受付と照らして点検した。[確認方法](../../../outputs/planning-ab-final-20260929/review-protocol.md)、[画像付き根拠](../../../outputs/planning-ab-final-20260929/review-evidence.md)、[試行・予測付きJSON](../../../outputs/planning-ab-final-20260929/review-evidence.json)、[個別注記](../../../outputs/planning-ab-final-20260929/review-annotations.json)を参照。実装担当による非盲検の点検であり、全物体の正解ラベルや攻略手順の採点ではない。

### 1. 測定値が正しくても、説明する対象がずれる

ls20では白十字は不変で、青・橙のブロックが上へ5画素動いた。Aは事前に白十字をPlayerとしたまま「Playerが上へ移動した」と説明し、移動したブロックへの役割の付け直しは確認できない。1巡目には下端バーの2画素が変わったのに「バーは不変」とも説明した。

Bの1巡目は、白十字が移動し、青・橙ブロックが下へ動いたと説明した。これは生グリッドと逆。2巡目は白十字の不変を読めたが、Player移動・地図範囲変化という解釈の対象対応は解決していない。**概念化工程を省いても、役割と実測対象の混同は残った。**

### 2. 古い結果が今回の観測や実操作に混入する

vc33のBは両巡とも、1操作目の変化「(63,0)の1画素」を2操作目にも説明した。2操作目で変わったのは(61,0)と(62,0)であり、(63,0)は不変。2巡目の次計画には「(63,0)をクリックした」とも書いたが、実際のクリックは(47,31)。変化した場所と操作した場所も混同している。

同一観測で新しい操作結果がないのに再照合した例はAで2件、Bで1件あった。`current_invocation_result=null`でも過去の結果を説明できてしまう。照合数が操作数以上でも、新しい検証結果が増えたとは限らない。

### 3. 無変化を読めても、予測との比較や次の試行が改善しない

ft09のBは、1巡目4回・2巡目3回すべて(15,15)をクリックし、毎回グリッド差分0だった。無変化の観測自体は読めていた。

しかし1巡目の2〜4操作目は、行動前の予測が「可視変化なし」なのに、結果を「変化するという予測に反した」と判定した。現在の予測ではなく以前の説明を引き継いでいる。さらに、一箇所・一条件での無変化を、対象が操作不能だという広い結論へ拡張した。

2巡目の3操作目は可視変化を予測していたので、不支持の判定は整合していた。ただし同じクリックを繰り返す間、区別したい仮説や変更条件は具体化していない。**操作数の増加を、有益な実験や因果推論精度の向上とは数えられない。**

## 停止原因と、先に修正した遷移検証

- Bはls20・vc33の4試走で、過去観測の候補IDを再提出し、修正要求後も直らず停止した（各2回拒否）。現在の索引は渡しているが、履歴の候補IDとの混同を防げていない。参照の検証を緩める解決は採らない。
- Aの2巡目ls20は3操作後の照合で入力19,585 tokens、再試行19,593 tokensとなり、16,384の上限を超えた。[サーバーログ](../../../outputs/planning-ab-final-20260929/server-context-errors.log)。重複測定の整理だけでは履歴増加を抑えきれない。Bも長い走行で超過しないと確認できたわけではない。
- Aの2巡目ft09は、計画あり・再理解への遷移を2回拒否して停止した。先行修正は今回も働き、矛盾した計画・遷移の**受理は全試走で0件**。矛盾した出力の生成と修正失敗までは解消していない。

## 次に変更する範囲

**「行動計画だけ」より、計画→実行→結果照合→次の計画の接続を優先する。** 今回は工程削減で余裕が生まれても、その余裕を有益な試行へ使えなかった。

1. 一操作の記録に、試行ID・対象の現在参照と対応候補・事前予測・実クリック位置／操作・観測期間を固定する。照合は今回の実操作結果を優先し、未実行の試行を過去の結果で埋めない。候補参照の継続はホストの対応情報から提示し、曖昧なら保留する。
2. 位置・色・不変など測れる予測を実測と照合し、役割・因果の仮説と分ける。「予測が不支持」とした根拠が、その予測を参照しているかも確認する。今回のls20・vc33・ft09の具体例を回帰対象にする。
3. 次計画には、前回から何を変え、その結果でどの説明を区別するかを要求する。同じ試行でも条件変更や遅延確認などの理由があれば許す。対象に必要な差分が不足すると判明してから、前処理・提示の追加を選ぶ。
4. 入力は現在の試行、比較対象、予想外の変化を優先し、過去記録を観測ID付きで必要時に取り出す。これを共通の土台にして、まず記憶選択、次に独立した状況理解などを**一つずつ**外して比較する。

結果照合は残す。記憶選択40呼出し・49.2秒は削減候補だが、今回の一括変更だけでは、この工程だけを削った効果量は未確定。計画へすべてを統合する構成や新しい大規模ステートの追加は、今回の結果からは支持されない。
