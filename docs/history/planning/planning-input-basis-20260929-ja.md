## 結論

1. **単純な既知の操作効果・現在状態・目的を渡せば、次操作を選ぶ能力はある。** 小課題の操作選択8/8、目的達成済みの判定8/8、前提条件に応じた次操作4/4。ただし小さい既知ルールの課題であり、画像から未知ルールを獲得する能力の証明ではない。
2. **実盤面では、過去操作が唯一の具体的な操作例になると、その再提案に引かれる。** 仮説・物体候補・過去のモデル説明をすべて外しても、2回の無変化クリックの実測履歴から同じクリック4/4になった。大量入力だけが原因ではない。
3. **少数の具体的な「対象＋操作」の候補を渡すと、未試行側を選べる場面がある。** 画像を外しても、左右の2候補を固定して試行済み側だけが異なる実履歴を渡すと、候補順に依存せず未試行側へ選択が反転した。
4. **これはまだ、失敗結果を使った汎用的な計画更新ではない。** 結果を伏せても未試行側を選ぶ。再試行目的を与えても未試行側へ進む条件があり、目的を言い換えると先頭候補を選ぶ条件もあった。最小入力は用途別の候補までで、汎用的・安定的な構成の確定には至っていない。

ここでの「根拠」は、入力を入れ替えたときの選択の変化を指す。モデルが出力した理由文を内部思考・注意重みの直接観測とは扱わない。

## 既存比較から変更した点

[以前の少量入力比較](incremental-planning-inputs-20260929-ja.md)では、画像だけなら赤、候補を加えると白、過去の対象説明だけでも白、実操作の数値座標だけでも座標反復があった。しかし、これだけでは「選択を誘導する入力」と「目的達成に必要な入力」を区別できなかった。

今回は正解のある小さな対照課題を先に含め、実盤面の基準入力から仮説・候補・旧計画・旧理由を外した。画像は既存の保存画像を使用し、クリック履歴は実行ログの場所を自然言語で記述する。数値のクリック座標は新しい実測履歴へ渡さない。位置記述が実クリック点を含み、その小領域の色が一様であること、2回とも受付済みで全盤面の画素差分0であることを検証した。位置の言語化は人が作成した補助で、自動生成精度の評価ではない。

全要求は同じ短い質問 `What should you do next?` と同じ小さな出力schemaを使う。systemメッセージなし。`status`と`next_step`が必須、`action`・`target`・短い`reason`は任意。CLICK・特定候補の選択は強制しない。`done`・`need_information`も許す。Qwen3-VL-4B-Instruct Q4_K_M、temperature=0、max_tokens=1000。質問だけの条件にもこのschemaはあるため、モデルへの全入力が文字どおり質問一文だけという意味ではない。

## 1. どこまで計画できるか：正解のある対照課題32要求

### 操作効果と目的

2ボタンと1ランプの合成課題。左右のクリックでON/OFFになる観測記録を示し、左右の効果、目的ON/OFF、現在状態が目的達成済みかどうかを入れ替える。装置は決定的で、隠れた前提・遅延・蓄積効果がないと明示する。物体候補一覧、画像、モデルの仮説、思考マニュアルはない。

| 評価 | 結果 |
|---|---:|
| 目的未達時、正しいボタンを次操作として記述 | 8/8 |
| 目的達成済みなら追加操作不要と判断 | 8/8 |
| 前提条件が閉なら開ける、開なら起動する | 4/4 |

最初の8件のうち4件は、次操作の文自体は正しいが `status=done` とする不一致があった。**操作内容8/8と、契約を含む一貫した正答4/8を区別する。** 今回はユーザーの指定どおり、その不一致の修正へは進まない。

前提条件の課題では「カバーを開ける操作」と「カバーが開いているときだけ起動する操作」を交換し、現在のカバー状態も交換した。4件とも適切な次のボタンを選んだ。既知の短い因果関係を使う能力は確認できるが、長い多段計画・未知環境での因果発見の成功率とは異なる。

省略対照は、未達4ケースから目的・観測結果・利用可能操作の一覧を別々に外した12件。結果を外しても操作を推測する出力があり、情報不足を必ず表明するわけではない。操作一覧の省略時は操作内容3/4、statusまで含む正答2/4。過去テストにもボタン名が残るので、一覧省略を操作情報の完全な除去とは扱わない。

## 2. 実盤面で何に引かれるか：48要求

同一のft09画像を持つ2履歴。左上の一部を2回クリックして無変化、右上の一部を2回クリックして無変化、という実記録を使用。各条件2反復。G=目的、A=利用可能なCLICK、I=現在画像、H=完了済みの実測履歴、P=旧モデル計画、C=85件の物体候補、K=保存されたモデルの知識・仮説。

| 入力 | 観察 |
|---|---|
| 質問のみ | 2/2「タスクを開始する」。具体的なゲーム操作ではない |
| G | 2/2「観察する」等の一般的な提案 |
| G+A | 2/2「未探索の場所をクリック」。対象を特定できない |
| G+A+I | 2/2で左下の中央へのクリック案。実行・有効性は未検証 |
| G+A+I+1回のH | 左の履歴は2/2情報不足、右の履歴は2/2以前の場所へのクリック |
| G+A+I+2回のH | 4/4で履歴に書かれたクリック場所を再提案 |
| 上記＋P | 4/4で旧計画の白い四角へ提案が戻る |
| 上記＋K | 4/4で白い四角へ提案が戻る |
| 上記＋C | 以前の領域への提案が残る。1件は別候補IDを左上と誤記する。安定した別操作への改善ではない |
| 上記＋C+P+K | 右履歴2/2で白へ再提案、左履歴2/2は次の具体的操作なし |
| 2回のHから結果だけを伏せる | 3/4以前の場所を提案、1/4情報不足 |
| G+A+H、画像なし | 4/4情報不足。具体的な代替対象がない |

P/Kは追加した情報の組全体の効果であり、その中のどの単語が原因かまでは分離していない。ただし「旧仮説や旧計画を候補選択の中立な説明として足しているだけ」とは扱えないことが分かる。

今回の質問のみは一般論になったが、前の別schemaの比較では情報不足だった。空に近い入力の挙動も出力形式に依存するため、どちらかをモデルの普遍的な性質とはしない。

## 4. 少数の操作候補を足す：20要求

物体85件ではなく、試行済みのクリックと左下の未試行クリックの2候補を人が用意する。候補は「対象のどの部分に何をするか」という操作記述であり、プレイヤー・ボタン等の役割を認定しない。候補順を反転する。候補は出力schemaのenumにはせず、選択を強制しない。

- 探索目的＋2候補＋画像：未試行側4/4。一般的な「未知ルールを調べる」目的でも4/4で未試行側。
- 未試行効果の調査目的＋2候補、**画像なし**：未試行側4/4、すべて`act`。
- 4候補＋画像：4/4で未試行候補を選ぶ。未試行候補同士では並び順の影響が見られる。
- 再現性確認目的＋2候補＋画像：試行済み側4/4。

2候補＋画像の一部は、具体的な未試行対象を挙げつつ`need_information`だった。ここでも選択内容と実行契約を分ける。候補の生成は人の補助なので、エージェントが自力で適切な2候補を作れるという結果ではない。

## 5. 画像・操作一覧を外し、履歴だけを交換：22要求

左右の2つの実クリック位置を**両履歴で共通の操作候補**に固定する。画像なし、別項目の「利用可能操作はCLICK」もなし。候補にはCLICKと対象説明が含まれる。入力は目的・2つの操作候補・短い実測履歴。

左を試した履歴なら右、右を試した履歴なら左、という選択が候補順を逆にしても成立した。

| 条件 | 選択内容 |
|---|---|
| 一般的な探索目的 | 未試行側4/4 |
| 未試行の効果を調べる目的 | 未試行側4/4 |
| **結果だけを伏せる** | 未試行側4/4。うち1件は対象記述の数値が崩れる |
| 目的を省略 | 未試行側4/4。うち1件は対象記述の表記が崩れる |
| 履歴を省略 | 2/2情報不足 |
| **再現性確認の目的** | 未試行側4/4。目的に合わない |

この入力では、「どちらを試したか」は選択を反転させるが、「無変化だったか」は未試行側選択に必須でなかった。**成功したのは試行済み／未試行の選別であり、失敗結果の因果的な解釈を実証したわけではない。**

再現性目的の「最後の相互作用を繰り返す」を「最後のCLICKを同じ対象に繰り返す」へ変える8要求も追加した。元の目的では4/4未試行側、明示した目的では4/4先頭候補を選び、試行済み側と一致したのは2/4だった。目的の明確化だけでも安定した参照にはならなかった。

## 6. 操作と結果を同じ行へ結び付ける：16要求

さらに、長い対象説明と別の履歴を照合させる代わりに、2つの操作IDと試行結果を同じ行へ置いた。画像なし。`last_completed_action_id`も明示する。対象説明あり／なし、左右どちらが試行済みか、候補順、探索／再試行目的を変える。

```json
{
  "goal": "Investigate the unknown rules of this visual game.",
  "available_actions": [
    {"action_id":"A","control":"CLICK","completed_tests":2,"observed_effect":"no board change"},
    {"action_id":"B","control":"CLICK","completed_tests":0,"observed_effect":"not observed"}
  ],
  "last_completed_action_id":"A"
}
```

これは実際に使用したIDのみの入力の一例。IDから実対象への対応は実験側で保持する。これ単体でクリック位置を決められるという意味ではない。

- 再試行目的では説明あり4/4、IDのみ4/4で試行済み対象を指定・参照した。IDのみでは「最後と同じ対象」という相対参照も含む。
- 探索目的では説明あり／なしとも、具体的な未試行側の提案は2/4、残り2/4は情報不足。説明ありの2件には対象文の崩れもある。

短い表にすればすべて解決するとはいえない。今回の変更は命名・結果の配置・明示的な最後の操作参照をまとめて変えるため、名前単独の効果でもない。

## 現時点での最小入力の考え方

用途を分ける必要がある。

| 判断させること | 今回、判断に使えた情報 | まだ示せていないこと |
|---|---|---|
| 既知ルールに従って次操作を選ぶ | 目的、関係する現在状態、操作効果・前提条件 | 画像から未知の因果ルールを正しく獲得すること |
| 未試行の操作を選ぶ | 少数の具体的操作候補、どれを試したか | 失敗原因の推論や、その操作が有効であること |
| 特定の操作を再試行する | 具体的な目的、操作と履歴の明確な対応 | 入力形式・対象名・候補順が変わっても安定すること |
| 画像から次の候補を作る | 現在画像、操作可能な種類、調査目的 | 履歴が増えても適切な代替候補を自力で出し続けること |

**有望な最小入力候補は「目的＋少数の操作候補＋候補ごとの観測・試行状態」だが、汎用的に十分な構成として確定してはいない。** 画像・物体候補・継続知識を常に全部渡す必要があるという根拠はない。特に候補の選択と、候補の発見・根拠となる因果知識の獲得は別の能力として評価するべきである。

次の優先課題は、この小さい構成で目的・効果・前提条件・試行済み側を1つずつ交換し、どの情報で選択が切り替わるかを確認すること。最小構成の確認前に、不整合の受理処理やステートの調整へ戻らない。
