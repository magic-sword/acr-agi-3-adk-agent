## 自動出題

[observation_questions.py](../../../scripts/observation_questions.py)に、元画素のBEFORE・AFTERと操作名を受け取る`build_questions()`を実装した。正解ラベルやゲームの攻略ルールは引数に含めない。

各時点を既存のプログラムで独立に抽出し、対応候補を作った上で、候補ごとに次の3問を生成する。

1. この候補の位置は変化したか。
2. この候補の局所的な形・色配列は変化したか。
3. この候補の幅・高さは変化したか。

選択肢は固定で、`A = 不変 / B = 変化 / X = 判断できない`。例えば、青い矩形の位置が(14,16)から(15,16)に変わった記録を提示し、その個体の位置の変化だけを尋ねる。プレイヤー・ゴールなどの役割は付けない。

物体全体の「青だけ・橙だけ・両方」の組合せを列挙すると物体数に応じて選択肢が膨らむため、個体ごとの固定選択肢を採用した。対応済みのN個体なら3N問。新たな候補や対応不明の候補も残すため、単純な3Nより増えることがある。

前回の33組の観測画素から228問を自動生成した。抽出・対応づけ・出題までの処理時間は、ローカルで中央値6.36ms、最大80.52ms。モデル回答の時間は含めない。これは1回ずつの準備時測定で、独立した速度ベンチマークではない。

**この228問の生成検査と、後述する29問の出力設定比較は別の検証である。** 228問をQwenに回答させて認識精度を測ったわけではない。表の27/29を自動生成した全問題の精度として扱わない。

## 1トークンに制限する方法

現在のQwenサーバーの`/tokenize`で、A・B・C・D・E・Xが各1トークンであることを確認した。実際のトークンIDはそれぞれ32・33・34・35・36・55だった。

現在のllama.cppへの要求では、例えば次の設定を使える。

```json
{
  "max_tokens": 1,
  "grammar": "root ::= \"A\" | \"B\" | \"X\""
}
```

`max_tokens=1`は生成するトークンの上限。`grammar`は生成できる文字列を制限する。空白や説明文から始める回答を防ぐため、出力上限だけでなく、許可する選択肢の文字も制約する方式を推奨する。

これは現在のllama.cppで確認した設定であり、すべてのOpenAI互換サーバーが同じ`grammar`引数を受け付けるとは限らない。別のモデルでは、選択肢の文字が1トークンになるかも再確認する。

1トークンで打ち切るため、今回の終了理由は`length`になる。選択肢の1文字が完結した回答なら有効として扱った。JSONの途中切れと同じ判定にすると、正常な1文字回答を誤って失敗扱いしてしまう。通常の上限16の条件は、回答文字に加えて選択肢本文や終了トークンも生成し、使用トークン数は中央値4だった。

## 同じ入力での比較結果

前回の29問について、「短い前後の測定値」と「測定済みの変更」の2種類の入力を再利用した。画像は送らない。以下の3設定を各3回、順序を混ぜて測定した。

- 従来：出力上限16。
- 出力上限1のみ。
- 出力上限1＋許可文字制約。

計522要求＋ウォームアップ6要求。通常のQwen3-VL-4B-Instruct（Q4_K_M本体、Q8_0 projector）、temperature=0、`cache_prompt=false`。出力条件以外のメッセージは完全に同じ。別の推論・思考モードへの切替は行っていない。

| 入力 | 設定 | 3回とも正答した問題 | 許可文字だけの回答 | 実際に1トークン | 応答時間中央値 |
|---|---|---:|---:|---:|---:|
| 前後の測定値 | 上限16 | 27/29 | 18/87 | 0/87 | 157.3ms |
| 前後の測定値 | 上限1 | 27/29 | 87/87 | 87/87 | 99.0ms |
| 前後の測定値 | 上限1＋文字制約 | 27/29 | **87/87** | **87/87** | **99.5ms** |
| 測定済みの変更 | 上限16 | 27/29 | 21/87 | 0/87 | 141.1ms |
| 測定済みの変更 | 上限1 | 27/29 | 87/87 | 87/87 | 89.4ms |
| 測定済みの変更 | 上限1＋文字制約 | 27/29 | **87/87** | **87/87** | **87.9ms** |

3回の回答選択の揺れはなく、出力設定を変えても正誤が変わった問題はなかった。移動対象は全設定16/16、パネル内部変化は測定値4/5・測定済み変更5/5を維持した。前回残った操作間の統合などの誤りは、1トークン化では解消しなかった。

同一問題の3回の中央値同士で比を取り、その比の中央値を集計すると、文字制約付き1トークンは前後測定値で約1.45倍、測定済み変更で約1.60倍速かった。表全体の中央値同士の比とは集計方法が異なる。

反復は主に時間のばらつきを見るためであり、87問の独立した問題を解いたという意味ではない。今回の小さな合成問題群の結果で、未観測ゲームへの精度を保証しない。

## 高速巡回と「見落としなく」の区別

今回の短い入力では1問およそ0.09〜0.10秒だった。単純に直列実行するなら毎秒約10問程度が目安になるが、入力長、画像処理、通信、同時実行、キャッシュの有無で変わる。1トークン化しても入力の読取りや前処理は残る。各物体に3問を出す場合、10物体なら30問であり、全体の処理時間は問数に応じて増える。

**生成した質問を全件処理することと、画面内の全変化を確実に認識することは異なる。** 次の対策を試作に入れた。

- 抽出した各候補について、決まった種類の問いを必ず生成する。
- 対応が一意に決まらない候補を、近い場所や同じIDというだけで結びつけない。
- 全画素の差分を計算し、抽出候補の実際の支持領域で覆われない変更画素を残す。
- 未割当の変更画素や対応不明があれば、`requires_review=true`として再確認対象にする。

単体テストでは、既存の小物体抽出器が拾わない20×20の領域が出現した例に対して、質問が0件でも400画素の未割当変更を検出し、再確認を要求できた。逆に、未割当画素が0でも、物体のまとめ方・意味・個体の同一性が正しいことは保証しない。

また、プログラムの測定値だけで移動や配列差が確定する項目は、プログラムで直接記録する方が効率的である。Qwenの短い質問は、測定事実の解釈や関係の確認など、モデルの判断が必要な箇所へ使う余地がある。全測定項目をQwenに再判定させることが必須ではない。
