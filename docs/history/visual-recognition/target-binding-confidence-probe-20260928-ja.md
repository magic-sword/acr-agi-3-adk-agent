========================================================

**2トークンで「選択肢＋確信度」を出力することはできた。ただし、自己申告の確信度でも、選択トークンの確率でも、今回確認した誤対応に高い値が付く。** 複数該当と不明を扱う設計には、単一選択の迷いと、各候補への独立した一致評価を区別する必要がある。

追記：[推奨した候補別3分類＋出力確率の検証結果](candidate-match-validation-20260928-ja.md)。以下は先行する小規模な動作確認の記録。

ユーザー提示の[Jev紹介記事](https://qiita.com/nasuvitz/items/44f20ed515b9734afb26)を確認し、技術的な意味は[TypeSafe公式のConfidence](https://docs.typesafe.ai/confidence)と[Primitives](https://docs.typesafe.ai/primitives)を参照した。JevのChoice/Scoreのconfidenceは、返された確率分布の形から計算する統計量であり、別途生成した自己評価の文章・数字ではない。真偽を個別に評価するNoulはyesの確率を返す。

**小規模な動作確認**

[前回の候補結び付け評価](target-binding-quiz-20260928-ja.md)から5問を選んだ。単純な色、複数一致、対象不在、対象の分割、役割の根拠不足を1問ずつ。同じ「短い候補情報＋画像」で以下の2条件を各2回、計20要求実行した。

- 1トークン：前回と同じ選択指示に`logprobs=true, top_logprobs=20`を追加。
- 2トークン：選択肢の文字に続いて、その回答が正しいという自己申告の確信度0〜9を生成。0は確信なし、9は非常に確信あり。数値は確率とは定義しない。

既存ローカルQwen3-VL-4B-Instruct、temperature=0、cache_prompt=false、出力文法制約。要求順は固定seedで混ぜ、入力・正解を保存してから実行した。20回答すべてが有効な形式で、1トークン条件は実際に1トークン、2トークン条件は実際に2トークンだった。各条件内で反復差はなかった。5つの例を意図的に選んだ動作確認であり、一般的な正答率・校正性能・速度差の推定ではない。

| 問題 | 正解 | 1トークン回答 | その選択トークンのAPI確率 | 2トークン回答 |
|---|---|---|---:|---|
| 単純な色の四角 | D | D | 約100% | D9 |
| 同じ青い四角が複数 | X | C（誤答） | 99.81% | C9（誤答） |
| 緑の四角が存在しない | X | X | 約100% | X0 |
| 十字全体を表す候補がなく、断片だけ | X | B（誤答） | 86.33% | B9（誤答） |
| 静止画だけで「操作可能なプレイヤー」を特定 | X | F（誤答） | 98.57% | F9（誤答） |

表のAPI確率は選択トークンのlogprobを指数変換した値。実際にその対応が正しい確率ではない。今回の少数候補では各選択肢がtop_logprobsに含まれたが、これは一般には保証されない。現在のランタイムの上位20件指定では43候補すべての分布を取得できない。

特にC9・B9・F9は「高い自己申告値なら採用」だけでは除去できない。また、正解のXに0を付けたため、このプロンプトの数字は「選んだ回答が正しいという確信度」という指示にも一貫して従っていない。対象がないことに確信がある場合、本来はXへの確信度が高くてもよい。

参考の応答時間中央値は1トークン336ms、2トークン365ms。今回の入力・少数要求での結果であり、1トークン追加のコストを隔離した測定ではない（確信度の指示も追加している）。候補別に質問を増やしたときの総時間も未測定。

**分布の意味と複数対象**

「どれか1つ」を答えるときの分布がA=0.48、B=0.47、C=0.05でも、AとBの両方が該当するとは限らない。AかBかを区別できない場合にも同じ形になる。全候補の分布が平坦な場合も、「全部が同じ程度に該当」「どれも該当しない」「情報が足りない」を分布形状だけでは識別できない。

複数該当を表したい場合は、各候補について独立に「対象条件を満たすか」を評価する。例えばAへの一致評価0.95、Bへの一致評価0.94、Cへの一致評価0.03なら、AとBを同時に残す設計が可能。これらは合計1にする分布ではない。ただし、この例は設計の説明用であり、Qwenで実測した値ではない。

独立した一致確率なら、全候補が0に近いことは「該当なし」の根拠、0.5付近であることは「判断がつかない」の根拠になる。いずれもモデルの評価が実際の正誤と対応するよう検証が必要。複数の高い一致評価が出ても、問いが「該当するもの全部」なら集合として扱える一方、「特定の1個」なら依然として一意に特定できていない。

2トークンの1回答から得るのは、選んだ1候補とその自己申告値だけ。他候補の自己申告値は得られない。全候補の値を得るには、複数の短い質問またはより長い出力が必要。1トークンとlogprobsなら候補の出力確率を追加生成なしで取得できるが、独立した一致評価とは異なる。

**現在の構成で試せる次の方式**

[`fast_choice.py`](../runtime/retired-implementation-ja.md)は既に1トークン＋logprobsを取得している。[llama.cpp公式仕様](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)にも確率の取得方法がある。確率の取得位置、許可候補外のトークン、上位件数による欠落は確認して扱う。

次の測定候補は、候補ごとに「一致／不一致／情報不足」を1トークンで判定し、その確率も保存する方式。候補が入力に指定されていれば、出力に候補IDを再生成する必要はない。候補間の一致評価は独立に持ち、コード側で単一／複数／該当なし／保留へ集約する。画像と共通情報のプレフィックスを再利用する余地はあるが、現在の1スロット構成でJevの並列出力と同じ速度になるとは仮定しない。

評価には、候補単位の正誤に加えて、複数候補集合の完全一致、過剰な紐付け、取りこぼし、不明の判定、採用した回答の精度と採用率、選択肢順序への依存、観測1件全体の時間を使う。閾値を決める問題と最終評価問題は分ける。前回の「一意に決められないのでX」と、今回検討する「複数該当を列挙」は正解の定義が異なるため、過去の結果をそのまま複数対応精度に読み替えない。

今回は動作確認までで、この方式の精度向上や確率の校正は未測定。ランタイムは変更していない。
