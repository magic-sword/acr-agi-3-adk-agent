# 共通文脈の提示だけを変える比較実験

> 過去の実装・調査の記録です。現在の仕様・実行コマンドは[現行実装](../skill-learning-runtime-ja.md)を参照してください。旧APIと旧比較コマンドは削除済みです。

2026-09-25。[先行研究の検討](agent-consistency-research-ja.md)で提案したA/B比較の最初の実装。

## 変更理由と仮説

これまでの評価では、初期状態の認識文を繰り返す例と、クリックを目的としながら方向入力を選ぶ例があった。既存の送信ログには現在のIntent・前回操作・新しい観測が含まれていたため、情報の欠落だけでは説明できない。多数のJSONフィールドに埋もれた目標と実結果を、毎回短い共通文脈として先に提示すると、それらを利用しやすくなるかを調べる。

今回操作するのは提示だけ。状態遷移、Intent/Assessment/ActionIntentの型、モデル、画像、スキル、完了ツール、操作検証、HTTP・時間・手数の予算は条件間で共通。方針と操作を拘束する新しい仕様やcriticは追加しない。

## 根拠となる参考文献と採用範囲

- **Voyager**（Wang et al., 2023）: 公開実装の`render_human_message`は課題・最新状態・前回コード・実行エラー・批評を項目ごとに再構成する。今回は、明示的な文脈の再提示を参考にする。スキル学習やcriticの追加まで同時に導入しない。[論文](https://arxiv.org/abs/2305.16291)、[入力構築の公開実装](https://github.com/MineDojo/Voyager/blob/main/voyager/agents/action.py)
- **ReAct**（Yao et al., ICLR 2023）: 課題を、判断・操作・観測の連続した文脈の中で扱う。今回は前回操作・予測・観測結果を隣接して提示する設計の参考にする。[論文 §2](https://arxiv.org/pdf/2210.03629)
- **Inner Monologue**（Huang et al., 2022）: 場面記述や操作結果などの環境フィードバックを次の計画へ戻す。モデルの古い説明と現在の実観測を区別する設計の参考にする。[著者の研究紹介](https://innermonologue.github.io/)、[論文](https://arxiv.org/abs/2207.05608)

これらは「短い文脈を先頭へ追加するだけで、本環境の4Bモデルが改善する」と実証した文献ではない。本実験の具体的な提示順・長さ・追加方式はプロジェクト側の仮説である。Voyagerでも動的課題はHumanMessageに置かれており、systemへ格上げすること自体を根拠にはしない。

## 実装した条件

|条件|モデルへ送るもの|
|---|---|
|A: `baseline`|従来のsystem instruction、全context JSON、前後画像、状態別の末尾課題|
|B: `shared_brief`|Aの最初のuserメッセージの先頭に、同じcontextから機械的に取り出した短い共通文脈を追加。それ以外のpartをそのまま保持|

`context_presentation.py`（旧実装、現行から削除済み）が、推論や記憶更新をせず次を再掲する。

```text
現在のステート、観測stepと環境状態、利用可能ボタン
現在の目的、継続条件、中断条件（モデルの方針として表示）
前回発行した操作、前回の予測
実画面が変化したか、境界をまたいだか
Assessmentが現在／過去のどちらの観測に属するか
Assessmentのフィードバックと不明点（モデルの解釈として表示）
ホストが検出した再計画契機
```

各欄は最大240文字で切り詰めを明示し、不明点は最初の2件を表示する。全文は直後のJSONに残る。Noneはnullとして示し、初回の結果や達成状況を補作しない。元のAssessment.summaryを再掲しないのは、初期説明をさらに繰り返す量を増やさず、目標・結果に表示を絞るため。

ASSESSでもDELIBERATEでも、現在の呼び出しのcontextから再生成する。state用instructionのキャッシュへ動的な目標を書き込まない。ACTは従来どおりホスト処理。

厳密には、Bは**位置・見出し・短い再掲・入力長をまとめて変える条件**である。同じ意味情報を維持するが、トークン数は増える。位置だけの効果、同じ長さの別文を追加する効果とは分離していない。

既定値は`baseline`。`COGNITION_CONTEXT_PRESENTATION`またはbenchmarkの`--context-presentation`で切り替え、manifest、worker spec、モデル判断ログに条件名を保存する。条件名そのものをモデル入力へ追加することはしない。

## 実験計画と再実行

対象は公開ls20・vc33・ft09。同じゲーム版で各条件2回、各試行は新しい記憶とゲームから開始する。各ゲーム内で1回目A→B、2回目B→Aとして順序を入れ替える。既定では合計12ゲーム実行、各最大12操作・1レベル・90秒、ワーカー上限110秒。

```bash
make benchmark-context

# 条件を一つだけ実行する場合
docker compose run --rm --no-deps dev python scripts/benchmark_local.py \
  --games ls20 --context-presentation shared_brief

# 終了済み結果を再集計。モデルは呼ばない
python3 scripts/compare_context.py --analyze outputs/context-comparisons/<日時>
```

比較ドライバは`compare_context.py`（旧実装、現行から削除済み）。各試行に同じ[benchmark_local.py](../../scripts/benchmark_local.py)を使い、ソース・モデルファイル・依存パッケージ・予算・GPU等のmanifest値と環境ファイルのハッシュを照合する。不一致があれば比較を停止する。各試行の元ログとHTMLは保持する。

モデル要求は既存設定のtemperature=0。モデルサーバは共用したまま、同時に複数のゲーム評価を実行しない。キャッシュやGPU状態の影響を完全に消してはいない。順序反転はその偏りを軽減する設計で、各2回を独立な統計標本とは扱わない。

実走行ではrun_id・残り時間が試行ごとに異なり、選択行動が変われば以後の観測も変わる。同じ記録済み入力を全ターンに与える実験ではない。同一入力のときに提示以外が変わらないことは回帰テストで、初期画像・指示・ツール等の一致と条件の実反映は送信ログで別に確認する。

## 評価項目

- クリア数、操作数、モデル判断とHTTP要求数、トークン数、時間、停止理由。
- 実画面に変化があった次のASSESSで、前のsummaryを完全一致で繰り返した件数と対象件数。
- 方針にclick語があるのに非CLICK操作を出した件数。これは準備移動などを含み得る**要確認候補**で、意味的不一致の確定件数ではない。
- 無変化の操作反復、提出訂正、再計画の頻度、スキルの実ロード。
- 元の認識・方針・操作・画像を照合した具体例。

文章の一致だけで誤認識と判定しない。無関係な表示だけが変わった場合、同じ認識が適切なこともある。異なる文章になっただけでも改善とは呼ばない。

## 検証記録

回帰テスト110件が成功。新しいテストでは、同じ記憶・観測・モデル応答を使った初回、方針更新、通常継続、レベル境界について、Bの先頭の共通文脈を除けば、実HTTP形式の入力がAと一致することを確認した。system、ツール宣言、全JSON、画像、末尾課題、予算も比較している。

比較ドライバの3テストも成功。順序反転、ソース差し替えの検出、比較可能な実画面変化だけを同文判定の分母とすることを確認した。

### 認識・方針の具体例

1. **ls20のB、1回目:** step1で初期説明から操作後の説明へ一度更新した。しかし「青い対象が32,32、橙の対象が34,48に新しく現れた」という記述は実観測と合わない。元の色IDは32,32が4→4、34,48が9→3で、PNGもその新規出現を支持しない。step2以降は更新後の同じ文を繰り返した。
2. **ls20のB、2回目:** 初期summaryの更新自体が見られず、変化後の同文は6 / 6。1回目の更新は安定して再現していない。
3. **vc33のB:** 発行済みのCLICKを先頭で再掲していても、summaryに「過去の操作なし」、feedbackに「操作していない」という記述が残る。受付ログと矛盾する。
4. **ft09のB:** 2回とも5操作へ増えたが、CLICKボタンを対象として記述し、同じ対象へのクリックを反復した。操作数の増加が対象理解や攻略につながった証拠はない。

[具体例の記録](../../outputs/context-comparisons/20260925T064149191789Z/qualitative-review.json)と各試行の`cognition/decisions.html`から確認できる。今回のA/Bでは元の「clickを目的に方向入力」という表層候補は出なかったため、その問題が改善したという評価もできない。

## 判断

**Bは時間内の操作数を増やしたが、認識・計画・操作の意味的一貫性の改善は確認できなかった。既定値はbaselineを維持し、shared_briefは比較用オプションとして残す。**

今回評価したのは、この短い再掲方式の各条件2回・3環境だけである。共通文脈という考え方全体が無効だと結論する実験ではない。次に原因を切り分けるなら、同じ記録済み観測を用い、実際の対象・直前の変化・目的と操作の対応を個別に確認する。先頭文を増やし続けることや、新しい状態を追加することを今回の結果だけで正当化しない。
