# 計画と抽象操作の高速実行の復元

2026-09-29。ユーザーの意図は、不要なカーソル調整・汎用記憶読み出しを削り、計画と抽象操作の高速実行を維持することだった。単一操作判断への置換と、その後の計画実装の削除は範囲を広げすぎた変更であり、訂正した。

## 現在の通常経路

```text
SAM／プログラム認識・対象仮説
  → understand：状況・最終目標・対象
  → backchain：最終目標に結び付く小目標
  → candidates：動詞＋対象の抽象操作候補
  → ground：候補を選び、複数ステップの実行手順にする
  → execute_step：現在の手順を具体的な1アクションへ高速変換
  → 実操作・受付・次の観測
      → 同じ手順の高速実行を継続
      → 必要な節目でreconcile：結果を照合し、計画を更新
```

`FocusedRuntime` を通常の生成先へ復元。計画の出力契約・交換可能な候補生成器・最終目標／小目標・複数ステップの手順・対象付き試行履歴を保持する。復元元は `46ac1b2` の契約・テスト、および `outputs/probe-execution-20260929/runtime/package/` に記録された計画実装。

高速実行は、抽象操作と現在のステップ・画面から、候補の具体的操作を1トークンで選ぶ。ステップを進めても同じ起動を保持する。操作の繰り返しごとに理解・逆算・候補生成をやり直す構成ではない。

## 戻さない処理

- カーソルの領域選択・移動・拡大調整のモデルループ。
- 汎用ノートを高速モデルで巡回して読み出す処理。
- 重複するスキル選択ステージ、旧比較ランタイム。

クリックは計画の対象IDに結び付け、現在マスク内の画素に置く。複数対象の候補では `target_object_id` でクリック対象を明示する。計画対象が失われた場合に古い座標を再利用しない。

計画対象の無変化・不明と別対象の実測変化に絞る履歴処理は維持した。汎用記憶読み出しステージを介さず、候補に対応する試行をプログラムで提示する。未操作の検証は高速モデルの完了選択肢を出さず、受付済みの観測を必要とする。

メモリschemaは16。schema 15の単一操作実験メモリを計画メモリへ読み替える移行処理はない。`SimpleRuntime` は比較・回帰確認用に残るが、通常の生成先ではない。

## 検証

復元した既存の計画テストと、現行の認識・履歴縮約・受付・パッケージ検証を実行し、全241テストが成功。追加の2段階手順テストでは、最終目標から生成した抽象操作 `move_to` を保持し、高速側が1段階目で上、2段階目で下を選択。同じ起動のまま進み、途中の理解・再計画やカーソル呼び出しがないことを確認した。

実モデル試走の記録は `outputs/planning-restored-20260929/`。初回は対象IDと領域参照の不整合で停止。次の試走では計画まで進んだが、未操作の達成を確認しようとして出力検証で停止した。これらを成功例とは扱わない。

対応として、理解時は既知の対象IDを選び領域参照はホストが補う方式と、新たな領域集合を選ぶ方式を区別した。クリックしか使えない場合は対象説明を出力契約で必須化し、未操作の結果照合では目標確定を選択肢から外した。さらに新規の領域集合も現在の参照だけを出力候補にした。全テストは `tests.log` に保存した。

`verified/` では、計画から高速選択したクリック1回を実行し、次の観測・結果照合まで進んだ。その後の理解で古い領域参照が出て停止した。参照制約を追加した最終コードの `release/` では、計画・高速判断まで進んだものの、観察だけで満たせる小目標を生成して未操作で完了を選び、再計画後の候補生成中に100秒の判断枠に達した。操作数は0、到達レベルは0。記録上の停止理由は `candidate_provider_invalid` だが、候補生成の例外処理がタイムアウトも同じ理由にまとめるため、候補内容の不正だけが原因とは断定できない。

したがって、計画・複数ステップ・高速変換の復元は回帰テストで確認済みだが、実モデルで安定して操作へ進むことや高速化を達成したとは言えない。観察だけで完了する小目標の生成と、候補生成のタイムアウト理由の区別が残る課題である。

単一操作版で計測した4操作・4モデル判断や履歴軽量化の時間は、その実験方式の結果である。復元版は計画生成と高速実行を分けるため、同じ呼び出し数・時間を主張しない。計画の意味的な品質やゲームの成功率は、復元・回帰テストと別の評価課題として残る。
