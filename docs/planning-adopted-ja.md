# 行動計画の採用方針と検証根拠

更新：2026-09-29。この資料を、行動計画・逆算計画の検証結果と採用方針の正本とする。物体認識については[認識の統合資料](visual-recognition-adopted-ja.md)を参照する。

**行動計画には「目的」「少数の対象と操作候補」「判断に必要な現在状態・試行結果」の3要素を渡す。目的は、既知の因果関係を使うコンパクトな逆算計画で小目標として生成する。** この方針を採用し、逆算計画の最適化や入力配置の追加検証はここで一区切りとする。

ここでの採用は、今後の構成に使う設計判断を意味する。今回の整理で通常ランタイムを変更したわけではなく、この組み合わせによる実ゲームの成功率を確認したという意味でもない。

## 1. 行動計画に必須とする3要素

| 要素 | 渡す内容 | 役割 |
|---|---|---|
| **目的** | 今回達成する小目標、または今回確かめる因果関係。最終ゴールとの関係も短く示す | 同じ操作の再試行と、別の操作への変更を選ぶ基準にする |
| **対象と操作の候補** | 現在扱える対象と、そこに適用する少数の抽象スキル。例：対象まで移動する、対象を作動させる | 過去の操作だけが唯一の具体的な選択肢になることを避け、代替案を比較できるようにする |
| **判断に必要な状態・結果** | 関係する現在状態、候補に対応する実行履歴と観測結果、既知の実行条件・効果。未試行・不明・仮説は区別する | 何ができるか、何を試したか、何がまだ分からないかを判断する材料にする |

3要素は設計上の必須項目とする。実験で、全環境に共通する数学的な必要十分条件や唯一の最適書式が証明されたわけではない。項目名やJSONの配置を固定することより、これらの内容が短く明確に渡ることを重視する。

### 対象と操作は「動詞＋対象」で表す

計画の候補は「右キーを1回押す」よりも、「右の壁まで移動する」「左のスイッチを作動させに行く」のような単位にする。高速モードが、到達・作動などの観測可能な終了条件まで連続操作を調整する。

動詞には実行条件・期待する効果・終了条件が対応する。対象名は完全な概念分類を要求せず、「左の物体A」のような参照でもよい。操作の効果から役割が分かれば更新する。自然言語で候補を作れたことと、実行可能なスキルを獲得したことは区別する。

確認できた操作と効果は、成立条件・実行手順・観測根拠を結び付けて再利用する。既知のスキルを組み合わせた行動も候補にできる。ただし、スイッチの操作成功と「その操作が扉を開く」という因果関係は別に確認する。スキルの自動獲得・合成による継続的な性能向上は、今回実証した成果には含めない。

精密なクリック座標と位置合わせは高速実行側の仕事とする。行動計画には、その判断に必要な場合だけ位置情報を渡す。画像、全物体候補、古い仮説を常に全部加える構成にはしない。

### 状態と履歴は、今回の判断に必要な範囲を渡す

現在の位置や開閉状態は最新観測に対応させる。過去の試行には「どの対象に何を実行し、何が観測されたか」を残す。過去のモデルの予測や説明を、現在の事実として扱わない。

一方、「条件Cで操作Aをすると効果Bが起きる」「この外観の対象は操作主体である」といった知識は、成立条件・根拠を持つ継続知識として参照する。短期の観測と長期の知識を分ける原則は維持するが、特定のノート書式が反復を解消したとは扱わない。

## 2. 小目標を生成するコンパクトな逆算計画

逆算計画の役割は、**最終ゴールに向けて、次に達成する状態か、次に検証する因果関係を選ぶこと**とする。全手順の最適化を完了してから動く構成にはしない。

入力は、最終ゴール、関係する現在状態、既知の因果関係・スキルと、その不明点。出力は次の内容が分かる短い小目標に絞る。

| 小目標に含める内容 | 意味 |
|---|---|
| 達成・検証すること | 今回何を変えるか、または何を確かめるか |
| 最終ゴールとの関係 | なぜそれが必要か、どの前提を満たすためか |
| 確認する結果 | 何を観測すれば達成・支持・反証・不明と判断できるか |

例えば、次の関係を考える。

```text
最終ゴール：出口に到達する
必要な状態：扉が開いている
関係する仮説：左のスイッチを作動させると扉が開く
今回の小目標：左のスイッチを作動させ、扉が開くか確かめる
確認する結果：対象への操作成立と、扉の開閉変化
```

関係が既知なら達成のための小目標、関係が未知なら検証のための小目標になる。最終ゴール自体が不明な局面では暫定的なゴール仮説を扱う。上の例は採用方針を説明する例であり、この文面による実ゲーム成功の記録ではない。

これにより、前処理にも「操作対象に加え、離れた扉の変化を追う」といった具体的な要求を返せる。静止画だけで全概念を確定することより、計画と因果推論で必要になった対象・関係を観測することを優先する。

逆算計画が選んだ小目標を行動計画へ渡し、行動計画が動詞と対象を組み合わせ、高速モードが実行する。観測結果から小目標・仮説を更新する。**役割の分担を採用するのであって、独立ステートの増設や既存の複雑な遷移全体を採用する判断ではない。**

## 5. 参考背景と実装への引継ぎ

動詞と対象の組み合わせによる目標生成は[IMAGINE](https://proceedings.neurips.cc/paper/2020/file/274e6fcf4a583de4a81c6376f17673e7-Paper.pdf)、目的への有用性と現在の実行可能性を分ける考え方は[SayCan](https://say-can.github.io/)、実行可能なスキルを蓄積・合成する構成は[Voyager](https://voyager.minedojo.org/)が参考になる。これらは設計の背景であり、手元のQwenで同じ成果が実証されたことを意味しない。

既存コードには、目標の前提関係を持つ `Backchain` と、適用条件・効果・終了条件を持つ `Procedure` がある。[現在の定義](../agent/cognition/state.py)。これを踏まえ、実装時は次の分担を保つ。

- 逆算計画：最終ゴールに必要な達成・検証の小目標を生成する。
- 行動計画：3要素を基に、対象と抽象スキルを選ぶ。
- 高速モード：連続操作・位置合わせ・スキルの終了確認を行う。
- 結果照合：実行結果を小目標と照合し、観測と条件付きの知識を更新する。

以上を引継ぎ事項とする。現在値の併記、長い計画の最適化、追加の反復実験を自動的に再開しない。個別の検証資料11件は `docs/history/planning/` に保管し、本文中の「次に検証する」は当時の提案として読む。生ログ・再実行スクリプトは各詳細資料の元の保存先に残している。

## 6. 通常ワークフローへの実装

2026-09-29、通常の `create_runtime()` を [FocusedRuntime](../agent/cognition/focused_workflow.py) に切り替えた。候補生成は **交換可能な暫定実装** として独立させた。自律的な候補生成の精度が確定したという意味ではない。

```text
現在の対象・関係を把握 → コンパクトな小目標生成 → 候補生成 → 行動計画
                                                            ↓
現在対象を再取得 ← 結果照合 ← 連続操作・照準・受付済み観測
```

| 工程 | 入力・出力 |
|---|---|
| `understand` | 現在画像と測定候補から最大4対象と関係を把握。概念分類一覧は不要。`concept` は短い対象名として使用 |
| `backchain` | ゴール仮説、現在状態、条件付きの知識・スキル効果から、達成または検証の小目標を1つ生成。期待観測とゴールとの関係を明示 |
| `candidates` | 小目標、現在対象、操作・既知スキルから最大3件の「動詞＋対象」を提案。既定実装だけが現在画像も使う |
| `ground` | **`purpose`・`candidates`・`evidence` の3要素**から1候補を選び、継続・終了・再考条件付きの手順へ具体化 |
| `execute_step` / `aim` | 選んだ手順を連続実行。座標と照準は最新画像で決める。7は終了候補、8は結果照合 |
| `reconcile` | 起動IDが一致する受付済みの結果、実測、開始時／現在画像を照合。解釈・試行記録を更新して継続または再計画 |

通常経路から、汎用ノート巡回、概念分類の必須生成、長い目標階層、計画後の重複した `choose_skill` を外した。旧 `CognitiveRuntime` と比較用クラスは過去の検証の再現用として残す。物体測定、移動検知、意味質問、高速操作、照準、操作受付と観測の対応付けは共用する。監視図には旧比較経路も明示して残し、新しい出力契約と候補生成も読み取れるようにした。

### 候補生成の差し替え

契約は [candidates.py](../agent/cognition/candidates.py) の `CandidateGenerator` / `CandidateBatch`。入口から注入できる。

```python
runtime = create_runtime(game_id, candidate_generator=my_generator)

class MyGenerator:
    async def generate(self, request, propose):
        # request はランタイムから切り離した辞書。
        # 独自ルール等で CandidateBatch を返すか、既定モデルへ委譲する。
        return await propose()
```

`request` には観測ID、小目標ID、目的、現在対象、実測・試行結果、条件付き知識、既知スキルの概要を渡す。`propose()` は1バッチに1回までで、通常の修正要求・時間制限・ログ記録を使う。独自実装も同じ出力検証を通す。観測ID・小目標IDの不一致、未知の対象参照、候補の重複、未確認スキルの再利用は拒否する。候補がない場合は `missing_info` を返して再理解へ戻す。

既定モデルの暫定動詞語彙は `move_to / activate / attack / push / pull / manipulate / inspect / combine` と、支持された既知スキルの動詞。ボタン名を生成して修正要求を繰り返すことを避けるため、出力スキーマに提示する。語彙の十分性は未検証で、独自プロバイダーでは別の意味的動詞を返せる。

候補の `source=proposed` は未検証の提案。`source=reuse` は結果照合で支持された手順に限り、現在の対象への適用を再確認する。別対象への自動転用はまだ行わず、対象記述と効果が既知スキルと一致しない場合は新しい提案として扱う。提案スキルは最大4段階の連続操作を持てるが、既知スキルを組み合わせる自律学習の精度は未検証。

### 現在情報と過去情報の区別

メモリは schema 13。現在対象・候補は観測ID、小目標は固有ID、実行結果は起動IDで区別する。再計画時には現在対象を再取得して候補を作り直す。境界を越えた現在対象・候補・短期の試行記録は破棄する。

過去の試行には、何を試し、何が起き、期待とどう違ったかを残す。行動計画への入力には生のクリック座標、ノート本文、全領域の画素パターンを渡さない。実測の詳細と画像は監査ログ側に保持する。

結果照合の因果メモは出典付きの**条件付きモデル解釈**として別に保存する。手順の再利用登録には、その起動の受付済み結果と `matched` / `confirmed` が必要。生成しただけの手順、画素変化、検証の終了だけでは登録しない。これも因果関係の普遍的な証明ではなく、適用条件付きの支持である。モデルが勝利を確定することはない。

検証用手順は `probe_action_limit`（1〜16）を計画時に指定する。単一の作動確認なら1回、移動などなら複数回を許容し、指定回数の受付済み観測で無変化も含めて結果照合へ戻す。同じ操作を一律に禁止する仕組みではない。

### 残る暫定部分

- 対象を最大4件、候補を最大3件に絞る際の選び方と、動詞・対象の生成品質。
- 過去結果・条件付き知識は各直近3件、既知スキルは直近4件という小さな窓で提示する。意味による最適な検索ではなく、必要な古い知識を取り落とす可能性がある。
- 最初のゴール仮説や対象解釈の正確さ。簡潔な入力にしても、白い四角などへの偏りが消える保証はない。
- 未経験の対象へのスキル転用、条件の抽象化、複合スキルの自律的な獲得。

### 実装の検証
